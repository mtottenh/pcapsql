# Audit of the existing `pcapsql-duckdb` extension (local source only)

All citations are `path:line` relative to `/home/user/pcapsql` (HEAD `1415425`, workspace version 0.4.2). No web sources were used. The `duckdb` / `libduckdb-sys` / `duckdb-loadable-macros` crate sources are NOT vendored or cached on this machine (no `~/.cargo/registry` copy found), so anything about what those crates do internally is marked as inference or gap.

## 1. Dependencies, versions, build, packaging, ABI metadata, entrypoint

### Takeaway
The extension is a `cdylib` built on the high-level `duckdb` Rust crate (`vtab-loadable`, `vscalar` features) plus `duckdb-loadable-macros` 0.1's `#[duckdb_entrypoint_c_api]`, packaged by a hand-rolled Makefile + Python footer script declaring `C_STRUCT_UNSTABLE` ABI for DuckDB `v1.4.2`, linux_amd64 only. It is not built, load-tested, packaged or released by any CI workflow (CI only compiles it and runs its pure-Rust unit tests via `--workspace`), and the manifest/Makefile (1.4 / v1.4.2) disagree with the lockfile (`duckdb`/`libduckdb-sys` 1.20000.0).

### Cited Findings
- Crate is `publish = false`, `crate-type = ["cdylib"]` — [pcapsql-duckdb/Cargo.toml:8-11](pcapsql-duckdb/Cargo.toml)
- Declared deps: `duckdb = { version = "1.4", features = ["vtab-loadable", "vscalar"] }`, `duckdb-loadable-macros = "0.1"`, `libduckdb-sys = { version = "1.4", features = ["loadable-extension"] }`, plus `hex`, `anyhow`, `thiserror`, `parking_lot`, `tracing`; `pcapsql-core` by path with **default features only** — [pcapsql-duckdb/Cargo.toml:13-33](pcapsql-duckdb/Cargo.toml)
- No `bundled` feature is enabled, so there is no in-process DuckDB to test against — [pcapsql-duckdb/Cargo.toml:18-20](pcapsql-duckdb/Cargo.toml); confirmed by comment "Unit tests for type conversion are not possible in a loadable extension because the DuckDB API is not initialized until the extension is loaded" — [pcapsql-duckdb/src/duckdb_schema.rs:47-49](pcapsql-duckdb/src/duckdb_schema.rs)
- Lockfile resolves `duckdb` to **1.20000.0** (depends on `arrow 60.0.0`, `duckdb-loadable-macros 1.20000.0`, `libduckdb-sys`) — [Cargo.lock:1971-1986](Cargo.lock); `libduckdb-sys` **1.20000.0** — [Cargo.lock:2855-2868](Cargo.lock)

- The 1.20000.0 lock entry was introduced by commit `a5e565e` "Release 0.4.2 (#152)", 2026-10-26 (`git log -S'1.20000.0' -- Cargo.lock`) — [Cargo.lock:1972](Cargo.lock)
- Makefile hard-codes `DUCKDB = /home/mtottenh/.duckdb/cli/latest/duckdb`, `DUCKDB_VERSION = v1.4.2`, `PLATFORM = linux_amd64`, `EXT_VERSION = 0.1.0` (workspace version is 0.4.2) — [pcapsql-duckdb/Makefile:5-8](pcapsql-duckdb/Makefile), [Cargo.toml:15](Cargo.toml)

- The section-size "varint" is not real LEB128: for sizes >= 128 it writes `struct.pack('<H', section_size | 0x8000)` (comment: "Simple varint encoding for sizes < 128") — [pcapsql-duckdb/scripts/append_metadata.py:27-33](pcapsql-duckdb/scripts/append_metadata.py)
- Entrypoint: `#[duckdb_entrypoint_c_api(ext_name = "pcapsql")] pub unsafe fn pcapsql_init(con: Connection)`; no `min_duckdb_version` argument is passed; it calls `vtab::register_all`, `udf::register_all`, `macros::register_all` — [pcapsql-duckdb/src/lib.rs:67-68,84-103](pcapsql-duckdb/src/lib.rs)

- No workflow, packaging file, README or FUZZING doc mentions DuckDB at all (`grep -ri duckdb .github packaging README.md` returns nothing); release builds only `-p pcapsql-datafusion` debs/rpms — [.github/workflows/release.yml:79-81,125-127](.github/workflows/release.yml); crates.io publishing covers only `pcapsql-core` and `pcapsql-datafusion` — [.github/workflows/publish-crates.yml:28-48](.github/workflows/publish-crates.yml); `packaging/` contains only `arch/PKGBUILD` — [packaging/arch/PKGBUILD](packaging/arch/PKGBUILD)
- Workspace default member is the CLI only (`default-members = ["pcapsql-datafusion"]`) — [Cargo.toml:11-12](Cargo.toml)

### Inferences
- Under duckdb-rs's version scheme the lockfile's 1.20000.0 very likely binds a much newer DuckDB C API than the `v1.4.2` the Makefile stamps into the footer; with `C_STRUCT_UNSTABLE` the footer's DuckDB version must match the loading DuckDB exactly, so the Makefile as committed is probably stale relative to the lockfile. Could not be verified locally (crate sources absent).
- Mixing `duckdb-loadable-macros` 0.1.15 (entrypoint) with `duckdb` 1.20000.0 is a second possible drift point; CI compiling it shows it type-checks, nothing shows it loads.
- The extension is effectively a developer-machine artifact: single platform, absolute path to one person's DuckDB CLI, unsigned (`-unsigned` required), no distribution channel.

### Gaps
- Exact DuckDB version / C API struct version that `libduckdb-sys 1.20000.0` targets, what `duckdb_entrypoint_c_api` 0.1.15 expands to (which `duckdb_ext_api_v1` access calls, which minimum version string), and whether the built artifact actually loads in any DuckDB release: not determinable from local files.
- No record (docs/CHANGELOG) of which DuckDB versions the extension has been tested against.

## 2. Table functions: what is registered and how bind/init/func work

### Takeaway
30 table functions are registered through duckdb-rs's safe `VTab` trait: `read_pcap(file, protocol)`, 27 macro-generated `read_<proto>(file)` functions, and `pcap_protocols()` / `pcap_schema(protocol)`. All scans are single-file, single-threaded behind a `Mutex`, fully parse every packet (`ParseScope::full()`), and implement none of: projection pushdown, filter pushdown, parallel/local state, cardinality, named parameters, globbing.

### Cited Findings
- Registration order: `register_read_pcap`, `register_registry`, `register_protocol_tables` — [pcapsql-duckdb/src/vtab/mod.rs:62-67](pcapsql-duckdb/src/vtab/mod.rs); via `con.register_table_function::<T>("name")` — [pcapsql-duckdb/src/vtab/read_pcap.rs:505-508](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/registry.rs:379-383](pcapsql-duckdb/src/vtab/registry.rs)
- 27 per-protocol VTabs generated by `define_protocol_vtab!` (ethernet, linux_sll, sll2, netlink, rtnetlink, vlan, arp, mpls, ipv4, ipv6, icmp, icmpv6, tcp, udp, dns, dhcp, ntp, http, tls, ssh, quic, vxlan, gre, gtp, ipsec, bgp, ospf) and registered one by one as `read_<name>` — [pcapsql-duckdb/src/vtab/protocol_tables.rs:408-477,480-521](pcapsql-duckdb/src/vtab/protocol_tables.rs); this list is hand-maintained (matches the 27 parsers in core's `default_registry`, guarded only by a unit test) — [pcapsql-duckdb/src/vtab/protocol_tables.rs:527-568](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- `read_pcap` parameters: two positional VARCHARs (file_path, protocol_name); `read_<proto>`: one VARCHAR; `pcap_schema`: one VARCHAR; `pcap_protocols`: none. Only `parameters()` is implemented — no named parameters anywhere — [pcapsql-duckdb/src/vtab/read_pcap.rs:294-299](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:432-434](pcapsql-duckdb/src/vtab/protocol_tables.rs), [pcapsql-duckdb/src/vtab/registry.rs:190-192,354-356](pcapsql-duckdb/src/vtab/registry.rs)
- **bind**: reads parameters with `bind.get_parameter(i).to_string()`, builds a fresh `default_registry()`, looks the protocol up, and calls `bind.add_result_column` for `frame_number` (UBIGINT) + every `protocol.schema_fields()` entry; unknown protocol → `DuckDbError::InvalidParameter` listing available parsers. The file is not touched at bind time — [pcapsql-duckdb/src/vtab/read_pcap.rs:86-150](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:73-112](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- `frames` pseudo-protocol (only via `read_pcap(file,'frames')`): columns `frame_number` UBIGINT, `timestamp` BIGINT, `length` UINTEGER, `original_length` UINTEGER, `link_type` USMALLINT — [pcapsql-duckdb/src/vtab/read_pcap.rs:97-111](pcapsql-duckdb/src/vtab/read_pcap.rs); timestamp is microseconds computed as `packet.timestamp_ns / 1_000` (nanosecond precision from core is dropped; not a TIMESTAMP type) — [pcapsql-duckdb/src/vtab/read_pcap.rs:220](pcapsql-duckdb/src/vtab/read_pcap.rs)
- Protocol tables carry **no timestamp column**; only `frame_number` + parser fields, so time requires a join on `frame_number` against a second scan of `read_pcap(...,'frames')` — [pcapsql-duckdb/src/vtab/protocol_tables.rs:84-104](pcapsql-duckdb/src/vtab/protocol_tables.rs), [pcapsql-duckdb/src/lib.rs:27-30](pcapsql-duckdb/src/lib.rs)
- **init**: fetches bind data through a raw pointer deref `unsafe { &*init.get_bind_data::<...>() }`, opens `FilePacketSource::open(path)` then `source.sequential_reader()`, stores `Mutex<Option<FilePacketReader>>`, another fresh `Arc<ProtocolRegistry>` (`default_registry()` again), `AtomicU64` frame counter, `AtomicBool done`. File-open errors therefore surface at init, not bind — [pcapsql-duckdb/src/vtab/read_pcap.rs:152-170](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:115-133](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- Init data is a single global object ("shared across threads when parallel execution is enabled" per its doc comment) — there is no per-thread/local init state, no `set_max_threads`, and `func` holds `init_data.reader.lock()` for the whole chunk, i.e. the scan is serialized — [pcapsql-duckdb/src/vtab/read_pcap.rs:61-77,185-192](pcapsql-duckdb/src/vtab/read_pcap.rs)
- **func**: `reader.process_packets(BATCH_SIZE, |packet| ...)` with `BATCH_SIZE = 2048`; each packet is fully parsed by `parse_packet(&registry, link_type, data, &ParseScope::full())`, and layers whose name equals the requested protocol are written to the output chunk — [pcapsql-duckdb/src/vtab/read_pcap.rs:39,211-263](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:175-211](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- Semantic inconsistency: `read_pcap(f,'tcp')` emits **all** occurrences per frame ("NO break - include all occurrences for tunnel support") while `read_tcp(f)` `break`s after the first occurrence — [pcapsql-duckdb/src/vtab/read_pcap.rs:235-251](pcapsql-duckdb/src/vtab/read_pcap.rs) vs [pcapsql-duckdb/src/vtab/protocol_tables.rs:186-201](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- Batch termination hack: the callback returns a fake `Error::Io(ErrorKind::Interrupted, "batch full")` to stop, and the caller recognises it by **string matching** `e.to_string().contains("batch full")` — [pcapsql-duckdb/src/vtab/read_pcap.rs:254-272](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:203-220](pcapsql-duckdb/src/vtab/protocol_tables.rs). Core documents and tests that a callback error still consumes the delivered packet — [pcapsql-core/src/io/pcap_stream.rs:408-415,723-760](pcapsql-core/src/io/pcap_stream.rs); before that fix "the DuckDB extension ... emit[ted] a duplicate row and drift[ed] frame numbers every 2048 rows" (#118) — [CHANGELOG.md:104-107](CHANGELOG.md)
- Error swallowing: any other reader error is treated as end of data (`Err(_) => { // EOF or actual error  done.store(true) }`), so a corrupt/truncated capture or I/O failure yields a silently short result rather than a DuckDB error — [pcapsql-duckdb/src/vtab/read_pcap.rs:273-276](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:221-224](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- Frame numbers are generated by the extension's own `AtomicU64` counter, not taken from `PacketRef`/`PacketPosition` — [pcapsql-duckdb/src/vtab/read_pcap.rs:212](pcapsql-duckdb/src/vtab/read_pcap.rs)
- No projection pushdown: `func` iterates every entry of `field_indices` and writes every column for every row; the design doc states the vtabs "receive DuckDB projection info and can adopt scoping as follow-up" and lists "its own projection pushdown via `ParseScope` is a tracked follow-up" — [pcapsql-duckdb/src/vtab/read_pcap.rs:360-501](pcapsql-duckdb/src/vtab/read_pcap.rs), [docs/query-scoped-parse-migration.md:285-287,657](docs/query-scoped-parse-migration.md)
- No filter pushdown, cardinality estimate, or statistics hooks appear anywhere in the crate (the only `VTab` items implemented are `bind`, `init`, `func`, `parameters`) — [pcapsql-duckdb/src/vtab/read_pcap.rs:82-300](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:413-435](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- No globbing / multi-file: bind stores exactly one `file_path: String` and init opens exactly that path — [pcapsql-duckdb/src/vtab/read_pcap.rs:44-55,156](pcapsql-duckdb/src/vtab/read_pcap.rs)
- Every table-function call independently opens and re-parses the whole capture; the documented join idiom `read_tcp(f) JOIN read_dns(f) USING (frame_number)` therefore parses the file twice with full parsing each time — [pcapsql-duckdb/src/lib.rs:27-30](pcapsql-duckdb/src/lib.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:119-125,179-184](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- `read_pcap.rs` and `protocol_tables.rs` duplicate ~250 lines (`output_parsed_row`, the func loop) nearly verbatim — [pcapsql-duckdb/src/vtab/read_pcap.rs:339-502](pcapsql-duckdb/src/vtab/read_pcap.rs), [pcapsql-duckdb/src/vtab/protocol_tables.rs:242-403](pcapsql-duckdb/src/vtab/protocol_tables.rs)
- Registry functions: `pcap_protocols()` → (name VARCHAR, description VARCHAR, field_count UINTEGER) from `registry.all_parsers()` + a hard-coded `frames` row and a hard-coded description `match`; `pcap_schema(p)` → (column_name, column_type, nullable) with a second, separately maintained `DataKind`→type-name mapping (which prints `FixedBinary(n)` as `BLOB[n]` although the real column is plain BLOB) — [pcapsql-duckdb/src/vtab/registry.rs:25-57,94-128,230-292,360-376](pcapsql-duckdb/src/vtab/registry.rs), [pcapsql-duckdb/src/duckdb_schema.rs:21-22](pcapsql-duckdb/src/duckdb_schema.rs)

### Inferences
- Because `process_packets` is capped at 2048 *packets* and `read_pcap` can emit more than one row per packet, a chunk can reach row index >= 2048 inside one callback before the `row_count >= BATCH_SIZE` check (read_pcap.rs:236-254). If DuckDB's vector size is 2048 this would index past the vector (panic or OOB depending on duckdb-rs's `as_mut_slice` length). Not verified — crate source unavailable; no test covers it.
- With one mutex-guarded reader and no local state, DuckDB cannot parallelize the scan, whereas core already offers `SeekablePacketSource::partitions` / `reader_at` (pcapsql-core/src/io/source.rs:163-175) that a local-init-per-thread design could use.
- `default_registry()` is rebuilt at every bind and every init; cheap but indicative that there is no extension-level shared state.

### Gaps
- Whether duckdb-rs's `VTab` trait at the locked version offers `supports_pushdown`, `named_parameters`, local init, or cardinality hooks that the code simply does not override: cannot be confirmed without the crate source.

## 3. Schema derivation and writing rows into data chunks

### Takeaway
Column types come from core's engine-neutral `DataKind` via a 13-arm match; values are written row-at-a-time, column-by-column, dispatching on the *runtime `FieldValue` variant* (not the declared column type) through `unsafe as_mut_slice::<T>()` casts, with a `HashMap<String,usize>` lookup and a `CString` allocation per string. Lists are buffered in a side builder restricted to four element types.

### Cited Findings
- `to_duckdb_type`: Bool→BOOLEAN, UInt8/16/32/64→UTINYINT/USMALLINT/UINTEGER/UBIGINT, Int64→BIGINT, Int8→TINYINT, Float64→DOUBLE, String→VARCHAR, Binary and `FixedBinary(_)`→BLOB, `TimestampMicros`→BIGINT ("DuckDB uses TimestampS for seconds, we store microseconds as Bigint"), `List(inner)`→LIST — [pcapsql-duckdb/src/duckdb_schema.rs:10-30](pcapsql-duckdb/src/duckdb_schema.rs)
- Column names are the core descriptor names verbatim, which are dotted (e.g. `dns.answer_ip4s`, `ipv4.src_ip`), so SQL must quote them (`"dns.answer_ip4s"`); at write time the prefix is stripped (`field_name.split('.').next_back()`) to look up the parser's short field name — [pcapsql-core/src/protocol/dns.rs:102-146](pcapsql-core/src/protocol/dns.rs), [pcapsql-duckdb/src/lib.rs:43](pcapsql-duckdb/src/lib.rs), [pcapsql-duckdb/src/vtab/read_pcap.rs:365-370](pcapsql-duckdb/src/vtab/read_pcap.rs)
- Per row, `output_parsed_row` iterates the `HashMap<String, usize>` of all columns, calls `output.flat_vector(col_idx)` afresh for each cell, then matches on `FieldValue`: scalars via `unsafe { vector.as_mut_slice::<T>() }[row] = v`; `Str`/`OwnedString`/`IpAddr` via `CString::new(..)` + `vector.insert` (strings containing NUL become NULL); `Bytes`/`OwnedBytes`/`MacAddr` via `vector.insert(&[u8])`; missing field → `set_null` — [pcapsql-duckdb/src/vtab/read_pcap.rs:360-501](pcapsql-duckdb/src/vtab/read_pcap.rs)
- The writer is value-typed, not column-typed: there is no check that the `FieldValue` variant matches the column's declared `DataKind` (contrast DataFusion's builder, which coerces by column builder type, e.g. UInt8→u32, IpAddr V4→u32, V6→FixedSizeBinary) — [pcapsql-duckdb/src/vtab/read_pcap.rs:411-497](pcapsql-duckdb/src/vtab/read_pcap.rs) vs [pcapsql-datafusion/src/query/builders/protocol.rs:173-186,235-275](pcapsql-datafusion/src/query/builders/protocol.rs)
- IP addresses: core declares `ipv4.src_ip`/`dst_ip` and `ipv6.src_ip`/`dst_ip` as `DataKind::String` and emits `FieldValue::IpAddr`; DuckDB writes them as text VARCHAR — [pcapsql-core/src/protocol/ipv4.rs:183-184,236-237](pcapsql-core/src/protocol/ipv4.rs), [pcapsql-core/src/protocol/ipv6.rs:86-87,147-148](pcapsql-core/src/protocol/ipv6.rs), [pcapsql-duckdb/src/vtab/read_pcap.rs:486-492](pcapsql-duckdb/src/vtab/read_pcap.rs). The crate docs nevertheless claim "IP addresses are stored as binary" and show `format_ip4(src_ip) FROM read_ipv4(...)` — [pcapsql-duckdb/src/lib.rs:35-40](pcapsql-duckdb/src/lib.rs)
- List columns: `ListColumnBuilder` accumulates `(offset,len)` entries and one of four typed buffers (u16, u32, String, Vec<u8>) across the chunk, then writes the child vector (`unsafe { child.copy(&values) }` for ints; per-element `CString`/slice insert otherwise), `set_len`, `set_entry` per row, and `set_null` for null rows — [pcapsql-duckdb/src/vtab/batch_builder.rs:16-29,106-163](pcapsql-duckdb/src/vtab/batch_builder.rs); rationale comment: "DuckDB's ListVector requires all elements to be written to the child vector first" — [pcapsql-duckdb/src/vtab/batch_builder.rs:12-14](pcapsql-duckdb/src/vtab/batch_builder.rs)
- `extract_list_values` only recognises UInt16, UInt32, Str/OwnedString, Bytes/OwnedBytes elements; anything else returns `ListExtract::Unsupported`, which is written as a NULL list — [pcapsql-duckdb/src/vtab/batch_builder.rs:179-257](pcapsql-duckdb/src/vtab/batch_builder.rs), [pcapsql-duckdb/src/vtab/read_pcap.rs:383-388](pcapsql-duckdb/src/vtab/read_pcap.rs)
- Core's DNS parser pushes AAAA answers as `FieldValue::IpAddr(V6)` into `answer_ip6s` (declared `List(FixedBinary(16))`) — [pcapsql-core/src/protocol/dns.rs:503-507,124-128,520](pcapsql-core/src/protocol/dns.rs); DataFusion's list builder handles `IpAddr::V6` — [pcapsql-datafusion/src/query/builders/protocol.rs:352](pcapsql-datafusion/src/query/builders/protocol.rs)
- Dead code kept under `#[allow(dead_code)]`: `insert_field_value`, `insert_string`, `insert_bytes`, `ListColumnBuilder::len/is_empty`; the module header calls itself "the DuckDB equivalent of pcapsql-datafusion's ProtocolBatchBuilder" — [pcapsql-duckdb/src/vtab/batch_builder.rs:1-3,166-175,272-273](pcapsql-duckdb/src/vtab/batch_builder.rs)
- CHANGELOG: NTP `Int8`/`Float64` columns — "the DuckDB extension writes them with the column's width" (#116) — [CHANGELOG.md:99-103](CHANGELOG.md)

### Inferences
- By the code paths above, `dns.answer_ip6s` in DuckDB is always a NULL list whenever it has elements (IpAddr → `Unsupported`), which makes the documented `format_ip6_list("dns.answer_ip6s")` example (lib.rs:45-46) non-functional. Reasoned from source; not executed.
- `format_ip4(src_ip)` from the crate docs would be applied to a VARCHAR column while `ip4_to_string` has an exact UINTEGER signature (udf/address.rs:113-118), so the example is likely wrong/stale.
- Per-cell `flat_vector()` handle creation, HashMap<String> iteration, and CString allocation make the row writer allocation-heavy; a direct C-API writer (`duckdb_vector_assign_string_element_len`, raw data pointers fetched once per chunk) or Arrow-batch reuse from the DataFusion builders would remove this.
- Because writing depends on HashMap iteration order only for which column is written when (not correctness), output is deterministic; but a parser emitting a narrower/wider variant than the declared kind would silently corrupt adjacent slots.

### Gaps
- No integration test exists to confirm actual column contents in DuckDB (see section 8).

## 4. File I/O and the core I/O abstraction boundary

### Takeaway
The extension reads only local paths through `pcapsql_core::FilePacketSource` (plain `std::fs::File`, sequential, no mmap, no index/partitions), getting gzip and zstd auto-detection for free; remote/cloud, stdin, lz4/bzip2/xz and mmap exist in core/DataFusion but are not reachable from DuckDB. Core's parsing stack is generic over synchronous `std::io::Read`, so a DuckDB-file-system-backed reader needs only a blocking `Read` (plus byte-offset open/seek and size/mtime for partitioned reads).

### Cited Findings
- DuckDB path: `FilePacketSource::open(&bind_data.file_path)` → `sequential_reader()` — [pcapsql-duckdb/src/vtab/read_pcap.rs:156-162](pcapsql-duckdb/src/vtab/read_pcap.rs)

### Inferences
- Remote files do not work in the DuckDB extension today: the path string goes straight to `std::fs`; `s3://...`, `https://...`, or DuckDB-registered file systems/secrets are never consulted.
- Minimum work for a DuckDB-file-system-backed source: (a) an adapter struct implementing `std::io::Read` over a DuckDB file handle → feed it to `StdinPacketSource::from_reader` or to `GenericPcapReader<DecompressReader<R>>` directly (sequential scans, compression included); (b) for parallel scans, implement `PacketSource + SeekablePacketSource` with `reader_at` = seek/open-at-offset on the DuckDB handle, plus size/mtime (or etag) for index validation — mirroring `FilePacketSource`/`CloudPacketSource`. Everything is synchronous, matching a blocking C file-system API; no async runtime is needed (unlike the object_store path).
- `FilePacketSource`'s internals (`FileInner` type alias, `detect_file`) are hard-wired to `std::fs::File`/`Path`, so reuse requires a new source type (or genericizing `FilePacketSource` over an opener trait) rather than a drop-in.
- The handle wrapper must be `Send` (reader) and the source `Send + Sync + Clone` — implies per-reader handles opened from a cloneable (path + filesystem-context) descriptor.
- Sidecar index writing next to the capture assumes a writable local directory; for remote DuckDB file systems the cloud-style local cache keyed by URL would be the applicable pattern.

### Gaps
- Whether `Read`-only adapters suffice for the index builder (`build_boundary_index` signature not inspected in detail) — index.rs imports `std::io::{Read, Write}` only (pcapsql-core/src/io/index.rs:30), suggesting Read is enough, but not confirmed line-by-line.
