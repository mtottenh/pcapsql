## 0. Versions, the two API families, and stability rules (context needed for every other question)

### Takeaway
As of November 2026 there are two separate C API families: the V1 API (`duckdb.h` / `duckdb_extension.h`, prefix `duckdb_`), which was fully stabilized in v1.5.6 and is a deliberately small surface (no filter pushdown, no glob, no multi-file reader), and the V2 API (`duckdb_v2.h` / `duckdb_extension_v2.h`, prefix `duckdb_v2_`), first shipped in DuckDB 2.0.0 (released 2026-10-21), which is far richer (filter pushdown, statistics, virtual columns, multi-file functions, glob, macros) but is 100% "unstable": a V2 extension binary only loads into the exact DuckDB build it was compiled against, and signatures already changed between the v2.0.0 tag and `main`.

### Cited Findings
- Latest release is v2.0.0 ("Cyanoptera"/"Cinnamon Teal", LTS), published 21 Oct 2026; v1.5.6 was published 28 Sep 2026; GitHub marks v2.0.0 "Latest", not pre-release — [GitHub releases](https://github.com/duckdb/duckdb/releases); announcement title "Announcing DuckDB 2.0.0 LTS 'Cinnamon Teal'" (search snippet only) — [duckdb.org](https://duckdb.org/2026/10/21/announcing-duckdb-200)
- Release notes for v1.5.6 state it "unifies C-API symbol versioning for clients and extensions and stabilizes all v1 APIs", "replaces the C API spec and code generation" and backports "DuckDB 2.0 API spellings"; v2.0.0 notes include "support for static linking C-API extensions" — [GitHub releases](https://github.com/duckdb/duckdb/releases)
- Lifecycle states: `unstable` = "present but not promised; may change or vanish without notice"; `stable` = "promised; signature and ABI slot are frozen from here on"; `deprecated`; `removed` — [VERSIONING.md](https://github.com/duckdb/duckdb/blob/main/api_spec/VERSIONING.md)
- V1 extension v-table has exactly two bands: "band v1.2.0 — 404 slots, always present" and "band v1.5.6 — 142 slots"; "nothing was stabilized between v1.2.0 and v1.5.6". So a V1 extension needing anything introduced after v1.2.0 (file system, client context, copy functions, config options, Arrow conversion...) must pin API version 1.5.6 (`build_loadable_extension_capi(my_ext 1 5 6 ${SOURCES})`, ABI type `C_STRUCT`), and then "Any DuckDB at or above it can load your extension" — [VERSIONING.md](https://github.com/duckdb/duckdb/blob/main/api_spec/VERSIONING.md)
- Alternative "pinned" build: `build_loadable_extension_capi_unstable(my_ext ${SOURCES})`, ABI type `C_STRUCT_UNSTABLE`; "DuckDB will only load your extension into if it has the exact same version you built against" — [VERSIONING.md](https://github.com/duckdb/duckdb/blob/main/api_spec/VERSIONING.md)
- The V1 spec's known-versions list on `main` ends at v1.5.6, and the only V1 declarations that differ between `duckdb.h@v1.5.6` and `duckdb.h@v2.0.0` are `duckdb_create_timestamp_tz_ns` / `duckdb_get_timestamp_tz_ns` (diff of the two headers); i.e. V1 received essentially no new functionality in 2.0 — [v1 metadata.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v1/metadata.yaml), [duckdb.h@v1.5.6](https://github.com/duckdb/duckdb/blob/v1.5.6/src/include/duckdb.h), [duckdb.h@v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/src/include/duckdb.h)
- V2: all 654 lifecycle entries in `api_spec/v2` on `main` are `[ "unstable", "v2.0.0", <date> ]`; zero are stable (grep count over the spec) — [api_spec/v2](https://github.com/duckdb/duckdb/tree/main/api_spec/v2)
- `duckdb_extension_v2.h` hard-errors without the unstable switch: `#error "the V2 C API has no stable surface yet: build with build_loadable_extension_capi_unstable or build_static_extension_capi_unstable, which tie the extension to this DuckDB version"`; header banner: "WARNING: this API is not yet stable, meaning it is only guaranteed to work for this specific DuckDB version." — [duckdb_extension_v2.h@main](https://github.com/duckdb/duckdb/blob/main/src/include/duckdb_extension_v2.h)
- "An extension targets either the V1 or the V2 C API, never both" (`#error "duckdb_extension.h and duckdb_extension_v2.h cannot both be included: pick one C API version"`) — [duckdb_extension_v2.h@main](https://github.com/duckdb/duckdb/blob/main/src/include/duckdb_extension_v2.h)
- V2 entrypoint: `DUCKDB_EXTENSION_ENTRYPOINT(duckdb_v2_extension_handle extension, duckdb_v2_context_handle context, duckdb_v2_error_info_handle *err) { ... }`, exported symbol `<name>_init_c_api_v2(struct duckdb_v2_extension_input *input)`. V1 entrypoint: `DUCKDB_EXTENSION_ENTRYPOINT(duckdb_connection connection, duckdb_extension_info info, struct duckdb_extension_access *access)` (exported `<name>_init_c_api`) — [duckdb_extension_v2.h@main](https://github.com/duckdb/duckdb/blob/main/src/include/duckdb_extension_v2.h), [duckdb_extension.h@main](https://github.com/duckdb/duckdb/blob/main/src/include/duckdb_extension.h)
- V2 calling convention: every function returns `DUCKDB_V2_ERROR` and takes a trailing `duckdb_v2_error_info_handle *err`; callbacks receive `(info, duckdb_v2_context_handle context, duckdb_v2_error_info_handle *err)`; a "context" is "a connection seen from inside DuckDB ... Within that scope a transaction is already active" reaching `duckdb_v2_context_get_factory()`, `duckdb_v2_context_get_config()`, `duckdb_v2_context_get_file_system()` and `duckdb_v2_context_log()` — [duckdb_v2.h@v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/src/include/duckdb_v2.h)
- V2 signatures are already churning: in the v2.0.0 tag strings are passed as `const duckdb_v2_str *` / `const duckdb_v2_identifier_t *` (e.g. `duckdb_v2_file_system_open(duckdb_v2_file_system_handle file_system, const duckdb_v2_str *file_path, duckdb_v2_file_open_options_handle options, duckdb_v2_file_handle *file, duckdb_v2_error_info_handle *err)`, `duckdb_v2_table_function_set_name(duckdb_v2_table_function_handle function, const duckdb_v2_identifier_t *name, duckdb_v2_error_info_handle *err)`), whereas on `main` the same functions take `const char *x, idx_t x_length` pairs (e.g. `duckdb_v2_file_system_open(duckdb_v2_file_system_handle file_system, const char *file_path, idx_t file_path_length, duckdb_v2_file_open_options_handle options, duckdb_v2_file_handle *file, duckdb_v2_error_info_handle *err)`) — [duckdb_v2.h@v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/src/include/duckdb_v2.h) vs [duckdb_v2.h@main](https://github.com/duckdb/duckdb/blob/main/src/include/duckdb_v2.h)
- On `main` but NOT in the v2.0.0 tag (spec diff): `table_function_add_virtual_column`, `table_function_set_stats_callback` + `table_function_stats_*`, `table_function_set_metrics_callback` + `table_function_metrics_*`, the whole `stats_*` module, `expression_check_statistics`, and scalar/aggregate stats callbacks — [v2 table.yaml@main](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml) vs [v2 table.yaml@v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/api_spec/v2/function/table.yaml)
- duckdb.org 2.0 docs reportedly say "the C API v2 is not yet stable. Its interface may change in upcoming releases" and that the release "ships a revamped C API v2 ... exposes components such as file systems and table functions to extensions" (search snippets; pages not fetched) — [docs/2.0/clients/c/v2/overview](https://duckdb.org/docs/2.0/clients/c/v2/overview), [announcement](https://duckdb.org/2026/10/21/announcing-duckdb-200)
- A header-only C++ convenience wrapper over the V2 C API exists in-tree (`tools/cpp/duckdb_cpp_extension.hpp`, `DUCKDB_CPP_EXTENSION_ENTRYPOINT(duckdb::cxx::Extension &extension, duckdb::cxx::Context &context)`), used by `test/extension/cpp_api_demo.cpp` — [cpp_api_static_demo.cpp](https://github.com/duckdb/duckdb/blob/main/test/api/capi/v2/static_extension/cpp_api_static_demo.cpp), [load_extension_capi_v2.test](https://github.com/duckdb/duckdb/blob/main/test/extension/load_extension_capi_v2.test)

### Inferences
- For pcapsql the choice is: (a) V1 pinned at 1.5.6 = one binary loads in 1.5.6, 2.0.0 and later, but with a minimal table-function surface; or (b) V2 = full reader feature set but one build per exact DuckDB version (same distribution burden as a C++ extension) and source churn until V2 is stabilized.
- Because the two headers cannot be mixed, a hybrid ("V1 for stability, V2 only for filter pushdown") is not possible in one extension binary.

### Gaps
- No statement found on when V2 will get a stable band. duckdb.org docs could not be fetched (host blocked), so the official docs' wording is second-hand.
- The `v2.0-cyanoptera` branch head (`cb56736`) differs from the v2.0.0 tag; I did not inspect whether a 2.0.1 backports any of the main-only V2 functions.
- Lifecycle dates inside the V2 spec (e.g. `2026-10-02` for stats callbacks that are absent from the 2026-10-20 tag) do not line up with the tag date; treat the tag diff, not the dates, as authoritative for "released vs main".

## 1. Table functions: bind / init / local init / exec, parameters, pushdown, parallelism, hints

### Takeaway
V1 offers the classic four callbacks with named parameters, projection pushdown, cardinality hint, max-threads and local init state, and nothing else (no filter pushdown, statistics, progress, virtual columns, ordering/partition info, or client context outside bind). V2 adds essentially the whole C++ `TableFunction` surface: filter-pushdown callback over bound expressions, statistics, progress, metrics, order preservation, partitioning, batch claiming, virtual `file_row_number`, and a context handle in every callback.

- Virtual columns (main only): `table_function_add_virtual_column(function, DUCKDB_V2_TABLE_VIRTUAL_COLUMN column, err)`; the enum has exactly one value, `TABLE_VIRTUAL_COLUMN_FILE_ROW_NUMBER` ("`file_row_number`, a BIGINT ... counting from 0"); "requires projection pushdown"; identified by column index "2^63 plus the value of the TABLE_VIRTUAL_COLUMN" — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- Profiler metrics (main only): `table_function_set_metrics_callback`, `table_function_metrics_set(info, name, name_length, uint64_t value, err)` — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- `table_function_set_get_bind_info_callback` with `table_function_get_bind_info_set_column_identifier` (field ids) and `_set_option` — used by the multi-file wrapper to map per-file columns — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- Error reporting: V1 uses `duckdb_bind_set_error(info, const char *error)`, `duckdb_init_set_error`, `duckdb_function_set_error`; V2 callbacks receive a "Borrowed error info handle to use to report errors that occur during the callback" (`duckdb_v2_error_info_handle *err`) — [v1 table_function.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v1/table_function/table_function.yaml), [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml), [v2 error.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/error/error.yaml)
- Client context: V2 passes `duckdb_v2_context_handle context` to every table-function callback (bind, init global/local, exec, progress, filter pushdown, ...) — [duckdb_v2.h@v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/src/include/duckdb_v2.h)

### Inferences
- V1 has no way to accept a WHERE predicate; a V1 `read_pcap` must emit every packet for projected columns and let DuckDB filter above the scan. Only projection pushdown (skip decoding unprojected columns) and LIMIT-driven early termination are available.
- In V1, a file handle needed in init/exec must be opened in bind (the only phase with `duckdb_table_function_get_client_context`), or the client context obtained in bind must be stashed in bind data; I found no documentation on whether a `duckdb_client_context` obtained in bind may legally be used in later phases/threads.
- Neither spec lists a table-in-table-out (in-out / lateral) table function, a "complex filter pushdown" over unbound expressions, dynamic (join) filter pushdown, sampling pushdown, or LIMIT pushdown hook; in V2 the table module contains no function with "in_out", "limit" or "sample" in its name.
- For pcap in V2: timestamp-range pruning is feasible via accepted filters (`ts >= X`) only if the reader can guarantee exact filtering; otherwise use the "offered again before global init" path as a skip hint, which needs no exactness.

### Gaps
- No table-in-table-out API was found in either spec, but I did not exhaustively read every V2 module description (only names), so absence is "not found by name".
- Whether `duckdb_v2_context_handle` handed to exec callbacks can run SQL is unknown: the query entry points I saw (`parse_sql`, `statement_bind`, `statement_execute_arrow`) take a `connection`, not a `context`, although the entrypoint doc calls the context one "to read and run queries through".

## 2. File system access from C

### Takeaway
Both API families let an extension CONSUME DuckDB's virtual file system (so paths routed to httpfs/S3/GCS/Azure and other registered file systems work, with settings/secrets resolved through the client context), but neither lets a C extension REGISTER a new file system. V1 (stable since 1.5.6) is open/read/write/seek/tell/size/sync/close only, with no glob, no exists, no positional read; V2 adds glob, exists, is-remote, `~` expansion, move/remove, positional `read_at`/`write_at`, parallel-access and external-file-cache flags, and named open hints. Neither exposes a compression option.

### Inferences
- Because V1 also goes through `FileSystem::GetFileSystem(ClientContext&)` (the same call V2's comment describes as the opener-pushing file system), V1 opens of `s3://`, `https://` etc. should also resolve secrets and be routed to httpfs when it is loaded; this is inferred from the implementation, not from a test or doc.
- No transparent gzip/zstd: with no compression flag in either API, a `.pcap.gz` / `.pcap.zst` opened through the C file system yields compressed bytes; pcapsql would have to bundle zlib/zstd and decompress itself (and loses seekability/parallel range reads on such files).
- In V1 there is no glob, so `read_pcap('dir/*.pcap')` cannot be expanded through DuckDB's file system (and thus not for S3 at all); local-only workarounds (own glob(3)) or requiring an explicit list parameter are the alternatives. In V2, `file_system_path_glob` or the multi-file wrapper (section 3) solves this.
- V1 lacks positional reads, so parallel scanning of one file needs one handle per thread (seek+read); V2's `file_read_at` + `FILE_FLAG_PARALLEL_ACCESS` allows a shared handle. Classic pcap has no index or sync markers, so intra-file parallelism is limited regardless; pcapng block structure or per-file parallelism are the realistic routes.

### Gaps
- No test or doc was found that exercises the C file system API against httpfs/S3 specifically; remote behaviour is asserted by API descriptions and inferred from the implementation.
- Whether `file_open_options_set_value` accepts a compression hint for some file system is unknown ("what they mean is that file system's business").
- The PR numbers that introduced the V1 file system API (v1.5.0) and the V2 modules were not identified.
- V1: thread-safety of one `duckdb_file_system` / `duckdb_file_handle` across threads is undocumented in the header text I read.

## 3. Multi-file reader (glob lists, `filename`, hive partitioning, union_by_name)

### Takeaway
V1 exposes nothing. V2 (already in the v2.0.0 tag, unstable) exposes a "multi-file function" wrapper: register a single-file table function, then wrap it so DuckDB supplies globbing, file lists, `filename`, `hive_partitioning`, `union_by_name` and per-file ordering.

### Cited Findings
- Functions (`unstable v2.0.0`, dated 2026-09-18): `multi_file_function_create(factory, &function, err)`, `multi_file_function_set_name`, `multi_file_function_set_single_file_function(function, name, name_length, err)`, `multi_file_function_set_reader_type` ("how the files the function reads are referred to in messages, e.g. 'Avro' or 'JSON'"), `multi_file_function_set_file_extension` ("With a file extension, a path that names a directory rather than a file reads the files with that extension inside it"), `connection_register_multi_file_function`, `extension_register_multi_file_function`, `multi_file_function_destroy` — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml); exact v2.0.0 declaration: `DUCKDB_C_API DUCKDB_V2_ERROR duckdb_v2_extension_register_multi_file_function(duckdb_v2_extension_handle extension, duckdb_v2_multi_file_function_handle function, duckdb_v2_error_info_handle *err);` — [duckdb_v2.h@v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/src/include/duckdb_v2.h)
- Handle description: "A multi-file function wraps an already registered table function that reads a single file, and adds everything that is needed to read many files at once on top of it: globbing, lists of files, hive partitioning, the `filename` column, `union_by_name` and the like" — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- Contract for the wrapped function: "must be registered before the multi-file function is, and must take the file to read as its only positional parameter, of type ANY. It is bound once for every file that is read, and receives ... the VARCHAR path of the file when there is nothing more to know about it, and otherwise ... a STRUCT holding the path in its `filename` field and the options to open the file with in its other fields - e.g. the size of the file ... (`read_x([{'filename': 'f.x', 'file_size': 42}])`). Opening the file with those options, set with `file_open_options_set_value`, lets the file system skip work ... A single-file function that takes a VARCHAR parameter instead is still accepted ... Every named parameter the single-file function declares is also a named parameter of the multi-file function" — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- After registration the function "can then be called with the path of a single file, a glob pattern, or a list of either, and accepts the options every multi-file function accepts (e.g. `filename`, `hive_partitioning`, `union_by_name`)" — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- Implementation builds on the engine's `TableFunctionMultiFileWrapper::CreateFunctionSet(std::move(single_file), name, settings)` — [capi_v2_func_table.cpp](https://github.com/duckdb/duckdb/blob/main/src/main/capi/v2/capi_v2_func_table.cpp)
- `file_row_number` virtual column is produced by a single-file function "when it is wrapped in a multi-file function" (main only) — [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)

### Inferences
- For pcapsql on V2 the natural design is `read_pcap_file(ANY)` (single file, projection pushdown, claim-batch callback) wrapped by `read_pcap` multi-file function with file extension `pcap`; cross-file parallelism, glob (incl. remote), `filename` and hive columns then come from the engine.
- On V1 all of this must be hand-built: accept `VARCHAR` or `LIST(VARCHAR)`, do own (local-only) globbing, add a `filename` column manually, and parallelize by handing files to threads via `duckdb_init_set_max_threads` + local init.

### Gaps
- No test file under `test/api/capi/v2/` references `multi_file_function` (grep finds it only in the spec, headers and implementation), so there is no in-tree usage example to copy and its maturity is unverified.
- Whether the wrapper handles compressed inputs for the wrapped reader is not stated.

### Inferences
- V1 macros/views: since the V1 entrypoint receives a live `duckdb_connection`, an extension can run `duckdb_query(connection, "CREATE OR REPLACE MACRO ...", ...)` during load; this is an inference from the entrypoint signature, not a documented pattern I verified, and such objects land in the user's current catalog/schema rather than being attributed to the extension the way V2's `extension_register_macro_function` does.
- V1 replacement scan from an extension requires obtaining a `duckdb_database` handle, which the entrypoint does not pass directly; how (or whether) C extensions do this in practice was not verified.
- TIMESTAMP/TIMESTAMP_NS/BLOB/LIST/STRUCT columns needed for packet data are all writable through the stable V1 vector API (raw `int64_t` micro/nanosecond arrays via `duckdb_vector_get_data`; BLOB via `duckdb_vector_assign_string_element_len`).
- Zero-copy Arrow hand-off from a table function is realistic only in V2 (`arrow_importer_append(consume=true)` then `vector_reference` into the output chunk); in V1, `duckdb_data_chunk_from_arrow` yields a new chunk and whether it shares buffers with the ArrowArray was not determined.

### Gaps
- Whether V1 `duckdb_data_chunk_from_arrow` is zero-copy, and whether its result can be referenced into a table function's output chunk, was not verified.
- No V1 function for creating views/macros or emitting log messages was found in the spec; did not verify every V1 module description.

## 5. What still requires the C++ API

### Takeaway
After V2, the C/C++ gap for a pure "reader" extension is small (and on V1 it is large: filter pushdown, statistics, multi-file reader, glob, progress). Things with no C entry point in either family: registering a file system, storage extensions / ATTACH-able catalogs, parser extensions, optimizer extensions, secret types/providers.

### Cited Findings
- Exhaustive registration surface of both specs (listed in section 2) contains no file system, storage extension, catalog, parser extension, optimizer extension, secret type/provider, collation, index type, or window function registration — [api_spec/v1](https://github.com/duckdb/duckdb/tree/main/api_spec/v1), [api_spec/v2](https://github.com/duckdb/duckdb/tree/main/api_spec/v2)
- V2 `instance_attach` / `attach_options_*` only attach existing database types from the embedder side; they do not define a new storage backend — [v2 instance.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/instance/instance.yaml)
- Filter pushdown, statistics, progress, partitioning, multi-file reading and globbing are absent from V1 and present (unstable) in V2, per sections 1–3 — [v1 table_function.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v1/table_function/table_function.yaml), [v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)
- The 2.0 announcement reportedly says extensions built against "the previous, unstable C++ API" must be rebuilt for DuckDB 2.0 (search snippet only) — [duckdb.org](https://duckdb.org/2026/10/21/announcing-duckdb-200)

### Inferences
- "Stable binary across DuckDB versions" plus "filter pushdown / multi-file" is currently not achievable by any route: V1 gives the former only, V2 and C++ give the latter only (both version-locked).
- Compressed-file reading through DuckDB's `FileCompressionType` auto-detect is effectively C++-only today.

### Gaps
- No authoritative DuckDB statement enumerating "C++-only" features was found; the list is derived from absence in the specs.

## 6. Working examples of C-API extensions that read files through DuckDB's file system

### Takeaway
I found no public end-to-end C-API extension that implements a file-reading table function on top of `duckdb_file_system_open` / `duckdb_v2_file_system_open`; available references are DuckDB's own unit tests and third-party language bindings that wrap the functions.

### Cited Findings
- In-tree usage: V1 test obtains the FS via `duckdb_connection_get_client_context` -> `duckdb_client_context_get_file_system` and exercises open/read/write/seek — [capi_file_system.cpp](https://github.com/duckdb/duckdb/blob/main/test/api/capi/v1/capi_file_system.cpp); V2 tests cover write/read/seek, positional read/write, open options with values, path queries, glob/move/remove — [test_capi_v2_file_system.cpp](https://github.com/duckdb/duckdb/blob/main/test/api/capi/v2/test_capi_v2_file_system.cpp)
- In-tree V1 demo extension (`extension/demo_capi/capi_demo.cpp`, 20 lines, built with `build_loadable_extension_capi` / `build_static_extension_capi`) only registers a scalar function — [demo_capi](https://github.com/duckdb/duckdb/tree/main/extension/demo_capi)
- Rust crate quack-rs wraps the V1 file system API ("File system access (DuckDB 1.5.0+)"; calls `duckdb_client_context_get_file_system`, `duckdb_file_system_open`, `duckdb_destroy_file_system`) — [quack-rs file_system.rs](https://docs.rs/quack-rs/latest/src/quack_rs/file_system.rs.html) (search snippet; third-party)
- Haskell `duckdb-ffi` 1.5.0.0 binds `duckdb_file_system_open`, `duckdb_create_file_open_options`, `duckdb_file_open_options_set_flag` — [Database.DuckDB.FFI.FileSystem](https://hackage-content-origin.haskell.org/package/duckdb-ffi-1.5.0.0/docs/src/Database.DuckDB.FFI.FileSystem.html) (search snippet; third-party)
- `duckdb/extension-template-c` describes itself as "(Experimental) C/C++ template for DuckDB extensions based on the C API"; "By default, this template only allows usage of the stable part of the API"; unstable via `USE_UNSTABLE_C_API` = 1 in the Makefile; its README does not mention `duckdb_extension_v2.h` — [extension-template-c](https://github.com/duckdb/extension-template-c)

### Inferences
- pcapsql would be an early adopter of the C file system API for a reader; expect to rely on the unit tests above as the reference for call sequences and error handling rather than on prior-art extensions.

### Gaps
- Did not search the community-extensions registry for C-API/Rust/Go extensions that may already use these functions; the Avro-style reader hinted at in the V2 docs text ("Avro", "avro" examples for `multi_file_function_set_reader_type`) suggests an internal consumer but none was located.
- Whether `extension-template-c` has a V2 branch/build path was not determined.
