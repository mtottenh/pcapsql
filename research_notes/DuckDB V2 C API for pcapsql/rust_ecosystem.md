# Rust ecosystem for DuckDB loadable extensions on the C Extension API (v1 and V2), state as of 2026-11-15

Method note: findings come from shallow clones of the upstream repos at their `main` HEADs on 2026-11-15 (duckdb-rs `b8447b5`, 2026-11-13; extension-template-rs `a679601`, 2026-11-13; extension-ci-tools `1eff33f`, 2026-11-12; community-extensions `e3001bd`, 2026-11-13; quack-rs `9ae1201`, 2026-10-30), from the DuckDB headers vendored in `libduckdb-sys` 1.20000.2 (`duckdb.tar.gz`), and from the crates.io API. `duckdb.org` and the GitHub issues API were NOT reachable from this session (network allowlist), so the DuckDB 2.0 release post, the official C API v2 docs and duckdb-rs issue threads could not be read first-hand.

## 1. duckdb-rs (`duckdb`, `libduckdb-sys`, `duckdb-loadable-macros`) and the new `duckdb-neo`

### Takeaway
As of Nov 2026 the upstream repo ships two wrappers on one sys crate: the classic `duckdb` 1.20000.2 (v1 C API; only scalar + table functions, projection pushdown only, no file-system wrapper) and the new beta `duckdb-neo` 0.20000.2 (V2 C API, `duckdb_v2.h`; table functions with local state, max_threads, projection AND filter pushdown, partitioning, progress, multi-file wrapper, DuckDB file system, copy functions, options, log sinks). Both track DuckDB v2.0.0. The whole V2 C API is still "unstable", so a `duckdb-neo` extension is pinned to one exact DuckDB build; the v1 C API was frozen at API version v1.5.6 and now contains the file-system/client-context/copy/config functions as stable entries.

Entrypoint macros (`duckdb-loadable-macros`)
- `#[duckdb_entrypoint_c_api(ext_name = "...", min_duckdb_version = "...")]`: both args optional. `min_duckdb_version` falls back to env `DUCKDB_EXTENSION_MIN_DUCKDB_VERSION`, then to the constant `DEFAULT_DUCKDB_VERSION = "v1.2.0"`; `ext_name` falls back to env `DUCKDB_EXTENSION_NAME`, then `CARGO_PKG_NAME`. The macro doc still says "Warning: experimental!". — [duckdb-loadable-macros/src/lib.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-loadable-macros/src/lib.rs)

### Inferences
- Calling raw `ffi::duckdb_*` functions the safe `duckdb` wrapper lacks (e.g. the v1 file-system API) is fully possible inside a loadable extension: they are ordinary `pub unsafe fn`s in `duckdb::ffi`/`libduckdb_sys` backed by the same function-pointer statics the wrapper uses, populated by the entrypoint macro. duckdb-zarr and laterite do exactly this (see section 4).
- Binary-compat consequence for v1: an extension that only needs functions in the pre-1.5.6 stable prefix can be stamped `C_STRUCT` with a low `min_duckdb_version` (e.g. v1.2.0) and load on many releases; one that calls the file-system/client-context functions must request API `v1.5.6` and will load on DuckDB >= 1.5.6 (1.5.6 and 2.0.x today). Before 1.5.6 the same functions required `C_STRUCT_UNSTABLE` and an exact-version pin.
- `duckdb_rs_extension_api_init` copies every field of the compile-time `duckdb_ext_api_v1` layout from the host's struct without gating by the requested version. If the host DuckDB is older than the bindings and its struct is shorter, the extra fields are read past the host's struct; calling such a function would hit either the null-assert panic or a garbage pointer. So with the `duckdb` crate, do not call newer-than-`min_duckdb_version` functions, and prefer setting `min_duckdb_version` to the API level actually used. (Inference from the generated code; not found stated in docs.)
- The `VTab` trait cannot express per-thread state. Parallel scans with `duckdb` 1.x have to keep all mutable state in `InitData` behind atomics/mutexes (it must be `Send + Sync`) plus `InitInfo::set_max_threads`, or drop down to `TableFunction::set_local_init` with hand-written `extern "C"` callbacks (which then bypass `contain_callback`).
- For pcapsql specifically, `duckdb-neo` is the only upstream Rust wrapper offering filter pushdown, real local state, progress, the multi-file wrapper and a safe file-system API, at the price of rebuilding for every DuckDB release.

### Gaps
- Could not read duckdb.org (release post "Announcing DuckDB 2.0.0", `docs/2.0/clients/c/v2/overview`, `docs/2.0/clients/rust/functions`): blocked by the session's network allowlist. A web-search snippet claims the official docs call C API v2 "not yet stable"; this matches the headers but was not read first-hand.
- Could not query duckdb-rs GitHub issues/PR discussions (API access denied), so issue-level history on file-system access, unstable API, parallel vtab and filter pushdown is not cited.
- Whether DuckDB formally guarantees that v1 API `v1.5.6` stays loadable in future 2.x releases is not confirmed from a primary DuckDB statement; the header still carries the "not yet stable" banner while two third parties (zarr Makefile, quack-rs) describe 1.5.6 as frozen/stable-with-caveats.
- No V2 slot for virtual columns was found by name; whether virtual columns are reachable another way in V2 was not investigated.

## 2. duckdb/extension-template-rs, build process, platforms, distribution

### Takeaway
Since 2026-10-23 the official Rust template is built on `duckdb-neo` and the V2 C API (`CAPI_VERSION=2`, `USE_UNSTABLE_C_API=1`, `TARGET_DUCKDB_VERSION=v2.0.0`), so its binaries load only in the exact DuckDB version they target. The build is `cargo build` -> (emcc link for WASM) -> `append_extension_metadata.py` footer, driven by `extension-ci-tools` makefiles; community publication is a `description.yml` with `language: Rust`, `build: cargo`, `requires_toolchains: "rust;python3"` and per-DuckDB-release refs.

### Inferences
- Despite the README's "(Coming soon) Works with community extensions", the community repo already points `rusty_quack`'s `ref` at a neo-based commit, and at least two third-party neo extensions are listed (section 4), so the community pipeline does build `CAPI_VERSION=2` Rust extensions for v2.0.0.
- Community extensions are built per DuckDB release by the pipeline anyway, so the exact-version pin of `C_STRUCT_UNSTABLE` mostly costs a rebuild (and a possible gap) at each DuckDB release rather than a distribution problem; it matters more for self-distributed binaries.
- A project needing to serve DuckDB 1.4 LTS, 1.5.6 and 2.0 can use the `ref`/`andium`/`variegata` keys to point at different commits/branches (e.g. v1 `duckdb` crate branch for old releases, neo branch for 2.0).

### Gaps
- The exact field order/content of the eight 32-byte footer fields was not read line by line; only the script's arguments, the length comment and the 256-byte signature padding were verified.
- Full list of platforms in `extension-ci-tools/config/distribution_matrix.json` for v2.0.0 (e.g. `linux_arm64`, `windows_arm64`, `windows_arm64_mingw` appear in descriptors' exclusion lists) was not extracted.
- Whether WASM builds of neo extensions work for `wasm_threads` out of the box is unclear; duckdb-zarr's Makefile documents manual workarounds (emsdk 3.1.71 feature pinning, extension-ci-tools#391 shared-memory flag) for its v1 build.

## 3. Alternative Rust crates

### Takeaway
The only actively maintained third-party SDK is `quack-rs` (0.20.0, 2026-10-30, single maintainer, pre-1.0, explicitly v1-stable-API focused with a self-published audit trail of past soundness bugs). `duckdb-extension-framework` is dead (last release 2022), and `duckdb-ext` / `quackapi` do not exist on crates.io.

### Cited Findings
- `quack-rs` 0.20.0 published 2026-10-30 (0.19.0 2026-10-23, 0.18.0 2026-10-02, 0.16.0 2026-08-19, 0.15.0 2026-07-16); ~8.4k downloads; repo tomtom215/quack-rs; "Rust SDK for building DuckDB loadable extensions on the DuckDB C Extension API"; MSRV 1.86.0; depends on `libduckdb-sys >=1.4.4, <1.20100`. — [crates.io quack-rs](https://crates.io/crates/quack-rs), [quack-rs README](https://github.com/tomtom215/quack-rs/blob/main/README.md)

- `duckdb-ext` and `quackapi`: crates.io API returns "crate does not exist" for both. — [crates.io duckdb-ext](https://crates.io/crates/duckdb-ext), [crates.io quackapi](https://crates.io/crates/quackapi)
- Forks/others seen in search results only (not examined): `spiceai_duckdb_fork` (fork of duckdb-rs on docs.rs), `vgi` 0.1.3 (has a `pushdown.rs`), `duckfn` 0.0.2. — [docs.rs spiceai_duckdb_fork](https://docs.rs/spiceai_duckdb_fork/1.4.4/src/duckdb/vtab/mod.rs.html), [docs.rs vgi](https://docs.rs/crate/vgi/0.1.3), [docs.rs duckfn](https://docs.rs/crate/duckfn/0.0.2)

### Inferences
- For a project that wants one binary across DuckDB 1.5.6 and 2.0.x with file-system access, the realistic choices are (a) `duckdb` 1.20000.x + raw `ffi` on API v1.5.6, or (b) quack-rs with `duckdb-1-5`; for filter pushdown / multi-file / true local state the only choice is `duckdb-neo` (V2, version-pinned).
- quack-rs carries bus-factor and soundness-history risk; upstream `duckdb-neo` is beta but maintained by DuckDB Labs with near-daily commits in Nov 2026.

### Gaps
- `vgi`, `duckfn` and other small crates were not evaluated; their relevance and maintenance are unknown.
- quack-rs table-function capabilities (local init, projection pushdown API names) were not verified in source, only its README claims.

### Inferences
- pcapsql's niche is unoccupied: `pcap_reader` has a fixed 8-column schema, no parallelism, no pushdown, bypasses DuckDB's VFS (so no `s3://`, no `enable_external_access` enforcement), and targets an old unstable-pinned DuckDB 1.3.0; it is unclear it is still built for 2.0.0.
- duckdb-zarr is the closest architectural template for a stable-ABI (v1.5.6) Rust reader with VFS + parallel + projection pushdown, and it also demonstrates the Makefile trick (`TARGET_DUCKDB_VERSION` overridden to the C API floor only for the metadata step) needed because extension-ci-tools uses one variable for both the API stamp and the test engine.
- duckdb_motorsport_telemetry and the official template's `sequence.rs` are the reference points for the neo/V2 route (safe `FileSystem`, filter pushdown).

### Gaps
- Only 11 of the ~80 Rust extensions were cloned and grepped; others may also use the DuckDB file system or parallel scans. Grep-based detection (`set_max_threads`, `supports_pushdown`, `duckdb_file_system_open`, `FileSystem::new`) can miss indirect usage.
- No Rust community extension implementing V2 filter pushdown in production was identified beyond the template example.
- Whether `pcap_reader` currently builds/publishes for DuckDB 2.0.0 and its download stats (duckdb.org/community_extensions unreachable) are unknown. No other pcap-reading DuckDB extension was found in the community repo by name, but a full-text search for "pcap" across all 425 descriptors was not run.

## 5. Known issues and gaps relative to the raw C API

### Takeaway
The main Rust-side hazards are: panics (contained by both upstream wrappers only for callbacks registered through them, and only with `panic = "unwind"`; in neo a panic deliberately invalidates the database instance), `Send + Sync` state requirements with no per-thread state in the v1 `VTab`, no filter pushdown at all in the v1 C API, version pinning for anything "unstable" (all of V2), and the security trap of reading files with `std::fs` instead of DuckDB's file system.

### Cited Findings
- Panics, v1 wrapper: contained via `catch_unwind` for functions registered through `register_table_function*` / `register_scalar_function*`; "A panic can poison or otherwise damage interior mutable state that later callbacks reuse, so implementations must preserve or restore state invariants during unwinding"; "a `panic = "abort"` build aborts first". — [crates/duckdb/src/vtab/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb/src/vtab/mod.rs)
- Panics, neo: "A panic is reported as an internal error instead, which invalidates the database: after the failed `LOAD`, every later query on it errors too." Same INTERNAL-error conversion applies to callback panics in `handle_unwind`. — [duckdb-neo/extensions.md](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/extensions.md), [duckdb-neo/src/builder_helpers.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/src/builder_helpers.rs)
- quack-rs: "`panic = "unwind"` is required: under `panic = "abort"` nothing can be caught, and a panic kills the user's DuckDB process"; raw callbacks installed by hand are unguarded; "A caught panic is still printed to stderr". — [quack-rs README](https://github.com/tomtom215/quack-rs/blob/main/README.md), [quack-rs known-limitations.md](https://github.com/tomtom215/quack-rs/blob/main/book/src/reference/known-limitations.md)
- Threading/ownership, v1 `VTab`: `InitData` and `BindData` must be `Sized + Send + Sync` ("The init data ... is global across threads"); the wrapper boxes them (`Box::into_raw`) and hands DuckDB a `drop_boxed::<T>` destructor; `func` only gets shared references (`get_bind_data() -> &BindData`, `get_init_data() -> &InitData`), so mutation needs interior mutability. — [crates/duckdb/src/vtab/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb/src/vtab/mod.rs), [crates/duckdb/src/vtab/function.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb/src/vtab/function.rs)
- Threading, neo: callbacks object is `Send + Sync + 'static`; `LocalState: Any + Send` is handed to `exec` as `Option<&mut LocalState>`, `GlobalState: Any + Send + Sync` as `Option<&GlobalState>`; "Recording accepted filters in shared `BindData` requires interior mutability". — [duckdb-neo/src/table_function/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/src/table_function/mod.rs)
- Filter pushdown: absent from the v1 C API bindings and from `VTab` (`supports_pushdown` only toggles projection pushdown via `duckdb_table_function_supports_projection_pushdown`); present in V2 (`duckdb_v2_table_function_set_filter_pushdown_callback`) and in neo (`TableFilterPushdownCallbacks`). — [libduckdb-sys/src/bindgen_bundled_version_loadable.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/libduckdb-sys/src/bindgen_bundled_version_loadable.rs), [duckdb-neo/src/table_function/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/src/table_function/mod.rs)
- Cardinality set at bind "is reported before any filter is pushed down and cannot be revised afterwards" (template README, V2). — [extension-template-rs README](https://github.com/duckdb/extension-template-rs/blob/main/README.md)
- Static linking vs function-pointer API: with `loadable-extension` the build "must not link against libduckdb"; all calls go through the function table, and calling before init panics with "DuckDB API not initialized or DuckDB feature omitted". neo's `build-extension-static` instead binds at link time and is mutually exclusive with `build-extension`; "A loadable extension cannot be linked statically". A web-search summary of the DuckDB Rust docs adds that enabling `loadable-extension` in a normal client application makes calls such as `Connection::open_in_memory()` panic (not read first-hand). — [libduckdb-sys/build.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/libduckdb-sys/build.rs), [duckdb-neo/src/extension.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/src/extension.rs), [DuckDB Rust client docs (search snippet only)](https://duckdb.org/docs/current/clients/rust/functions)
- Testing consequence: quack-rs provides separate `bundled-test` / `bundled-test-prebuilt` features because a loadable build cannot open an in-process DuckDB; the template tests via the DuckDB Python client and SQLLogicTest files. — [quack-rs Cargo.toml](https://github.com/tomtom215/quack-rs/blob/main/Cargo.toml), [extension-template-rs README](https://github.com/duckdb/extension-template-rs/blob/main/README.md)
- Security trap: "An extension that reads files with `std::fs` bypasses DuckDB's permission settings" (`enable_external_access`, `allowed_directories`); measured by quack-rs on DuckDB 1.5.6 and 2.0.0; DuckDB's file system also "resolves `s3://` and `http://` paths when `httpfs` is loaded". — [quack-rs known-limitations.md](https://github.com/tomtom215/quack-rs/blob/main/book/src/reference/known-limitations.md)
- Other C API traps documented by quack-rs: NULL rows of LIST/MAP vectors hold stale offset/length entries; declaring `VARIANT` in a function signature crashes DuckDB 2.0.0; a function that reads a setting must be marked volatile (v1 has only `volatile`). — [quack-rs known-limitations.md](https://github.com/tomtom215/quack-rs/blob/main/book/src/reference/known-limitations.md)
- Binary size: the template sets `[profile.release] lto = true, strip = true`; pcap_reader does the same. No measured sizes were found. — [extension-template-rs Cargo.toml](https://github.com/duckdb/extension-template-rs/blob/main/Cargo.toml)
- Toolchain floor: duckdb-rs 1.20000.x needs Rust 1.88 (edition 2024); quack-rs notes older toolchains resolve to 1.10506.x. — [duckdb-rs Cargo.toml](https://github.com/duckdb/duckdb-rs/blob/main/Cargo.toml), [quack-rs README](https://github.com/tomtom215/quack-rs/blob/main/README.md)

### Inferences
- A loadable extension built on the function-pointer API does not link DuckDB at all, so binary size is dominated by the extension's own dependencies (plus `arrow` 60, which the `duckdb` crate depends on unconditionally; `duckdb-neo` has no arrow dependency in `[dependencies]`).
- Mixing `duckdb` (v1) and `duckdb-neo` (V2) in one cdylib is not viable: the V2 header states "An extension targets either the V1 or the V2 C API, never both", and each API has its own entrypoint symbol and function table.
- Decision matrix for pcapsql: (1) need filter pushdown / multi-file globbing / progress / safe FS wrapper -> `duckdb-neo` 0.20000.x, accept `C_STRUCT_UNSTABLE` pin to each DuckDB 2.x release and beta API churn; (2) need one binary for DuckDB 1.5.6 + 2.0.x -> `duckdb` 1.20000.x `VTab` + raw `ffi` file-system calls stamped `C_STRUCT`/`v1.5.6`, with projection pushdown and `set_max_threads` only; (3) need DuckDB 1.4 LTS too -> v1 API floor v1.2.0 with no VFS access (or unstable pin per version), noting 1.4 support ends late Nov 2026.

### Gaps
- No primary-source statement was found on DuckDB's roadmap for stabilising parts of the V2 C API (i.e. when `C_STRUCT` V2 extensions become possible).
- No measurements of extension binary sizes or of callback overhead of the AtomicPtr trampolines were found.
- duckdb-rs issue/PR discussions on these topics could not be accessed, so there may be known bugs (e.g. around `set_local_init`, Arrow vtab, WASM) not captured here.
