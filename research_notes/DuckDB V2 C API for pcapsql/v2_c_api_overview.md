# DuckDB "V2 C API" / C Extension API: what it is, history, versioning and stability (state as of 2026-11-15)

Method note: `duckdb.org` and the GitHub API were not reachable from the research session. Website content was read from the site's source repo (`duckdb/duckdb-web`, raw files) and headers/source from `raw.githubusercontent.com/duckdb/duckdb` at the tags `v1.2.0`, `v1.3.0`, `v1.4.0`, `v1.5.0`, `v1.5.6`, `v2.0.0` and at `main` (fetched 2026-11-15). Two GitHub pages (Discussion #27525, PRs #24362 and #25916) were read through a summarising fetch tool, so statements attributed to them are paraphrases, not verbatim quotes, unless marked otherwise. Function names below were extracted mechanically from the headers.

## 1. Where does the quote come from, which release ships the V2 C API, and what is its status?

### Takeaway
The sentence is from the DuckDB 2.0 documentation ("C API v2" overview page and the C API overview page) and, in near-identical wording, from the DuckDB 2.0.0 release announcement of 2026-10-21. The C API v2 ships in DuckDB 2.0.0 (the latest release as of Nov 2026) but is explicitly **not stable**: every v2 function is behind an unstable switch, and stabilisation is a roadmap item "in flight" for DuckDB 2.1.

### Cited Findings
- Verbatim (docs): "DuckDB 2.0 ships a revamped C API, which is considerably more powerful than its predecessor. Among others, it exposes components such as file systems and table functions to extensions." Preceded by: "Warning The C API v2 is not yet stable. Its interface may change in upcoming releases." — [docs/2.0/clients/c/v2/overview (source)](https://raw.githubusercontent.com/duckdb/duckdb-web/main/docs/2.0/clients/c/v2/overview.md), rendered at [duckdb.org/docs/2.0/clients/c/v2/overview](https://duckdb.org/docs/2.0/clients/c/v2/overview). ### Inferences
- "V2 C API" = a new, separately named API family (`duckdb_v2_*` symbols, `duckdb_v2.h`), not a new minor version of `duckdb.h`. It is released in the sense that it ships in the 2.0.0 binaries and headers, but experimental in the sense that nothing in it carries a compatibility promise.
- No date for DuckDB 2.1 was found; given the 1.4 -> 1.5 -> 2.0 cadence (roughly 6-7 months between feature releases), spring 2027 is plausible but unconfirmed.

### Gaps
- The rendered duckdb.org pages and the release calendar (planned 2.1 date) could not be fetched; only the site's source repo was read.
- Whether a 2.0.1 patch release is imminent is unknown (only a `2.0.1-alpha` Java dev version string was seen).

## 2. Versioning / stability model (V1 stable vs unstable, ABI types, forward compatibility) and how V2 changes it

### Takeaway
V1's C extension API is a versioned function-pointer struct (`duckdb_ext_api_v1`) where an extension declares the minimum API version it needs and then loads in that DuckDB version and all later ones; v1.5.6 stabilised every remaining unstable V1 function and froze V1. In 2.0.0 the "unstable" ABI type (`C_STRUCT_UNSTABLE`) now means "C API v2, pinned to this exact DuckDB build", so a V2 extension today has **no cross-version binary compatibility**.

### Cited Findings
**Three ABI types and how the loader dispatches (DuckDB 2.0.0)**
- The extension metadata footer's ABI field is parsed as `C_STRUCT`, `C_STRUCT_UNSTABLE`, or `CPP` (empty = `CPP`); anything else is `UNKNOWN`. For `C_STRUCT` the footer also carries the C API version string. — [extension_load.cpp @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/main/extension/extension_load.cpp)
- Loader comment, verbatim: "Which C API family an extension targets. C_STRUCT_UNSTABLE always means V2: everything that was unstable in the V1 API was stabilized into v1.5.6, so a V1 extension pins that version rather than building against "unstable"." A `C_STRUCT` extension whose declared version is a v2.x.y version is also routed to V2. — [extension_load.cpp @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/main/extension/extension_load.cpp)
- Entrypoint symbols: V2 extensions export `<name>_init_c_api_v2`; V1 extensions export `<name>_init_c_api`. If a `C_STRUCT_UNSTABLE` binary lacks the v2 symbol the loader errors with: "Extensions built against the unstable C API, or against C API v2.x.y, must use the entrypoint from duckdb_extension_v2.h. To keep using the V1 C API, pin it with build_loadable_extension_capi(<name> 1 5 6 ...), which provides "<name>_init_c_api" instead." — [extension_load.cpp @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/main/extension/extension_load.cpp)
- Static-link order in 2.0.0 is "C++ first, then C API v2, then C API v1". — [extension_load.cpp @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/main/extension/extension_load.cpp)
- C++ (`CPP` ABI) extensions remain tied to one DuckDB version: "currently DuckDB extensions binaries are tightly bound to a single DuckDB version". — [Versioning of Extensions, docs 2.0 (source)](https://raw.githubusercontent.com/duckdb/duckdb-web/main/docs/2.0/extensions/versioning_of_extensions.md)

**V1 (`duckdb_extension.h`, `duckdb_ext_api_v1`)**
- The function-pointer struct was introduced in v1.2.0: "#error "the DuckDB C extension API struct was introduced in v1.2.0; cannot target an older version"". The V1 header only accepts major version 1. — [duckdb_extension.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension.h)
- From v1.2.0 through v1.5.0 the header's default `DUCKDB_EXTENSION_API_VERSION_*` stayed at 1.2.0; everything added later sat in `#ifdef DUCKDB_EXTENSION_API_VERSION_UNSTABLE` blocks. In v1.5.6 the default became 1.5.6 and the struct has a single new band `#if DUCKDB_API_VERSION_AT_LEAST(1, 5, 6)` with no unstable tail. — headers at [v1.2.0](https://raw.githubusercontent.com/duckdb/duckdb/v1.2.0/src/include/duckdb_extension.h), [v1.5.0](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.0/src/include/duckdb_extension.h), [v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h)
- Measured from the v1.5.6 header: 404 function pointers before the 1.5.6 band (the v1.2.0 stable surface) and 142 in the 1.5.6 band, 546 total. — [duckdb_extension.h @ v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h)
- PR #24362 "Unify C-API symbol versioning for clients/extensions, stabilize all v1 API's" (author Maxxen, opened 2026-07-31, merged 2026-08-03 into `v1.5-variegata`; forward-ported to `main` in #24435). Per the summarised PR page: all remaining unstable V1 symbols were stabilised in v1.5.6 because the upcoming V2 API has a different entrypoint and "unstable" will imply V2; the v1.2.0 vtable layout is a prefix of the new one (v1.2.0 exposes 404 slots, v1.5.6 exposes 546); extensions should pin the lowest version they need; contributors should not add new functions to the V1 C API; the plan is to deprecate V1 when DuckDB v2.0.0 ships and remove it in v3.0.0. The PR text reportedly says "about 189 functions were stabilized", which differs from the 142 struct slots counted above (the difference is unexplained; it may count `duckdb.h` symbols rather than vtable slots). — [PR #24362](https://github.com/duckdb/duckdb/pull/24362)
- The 1.5.6 release notes list: "#24362 – Unify C API symbol versioning for clients and extensions, stabilize all v1 APIs". — [Announcing DuckDB 1.5.6 (source)](https://raw.githubusercontent.com/duckdb/duckdb-web/main/_posts/2026-09-28-announcing-duckdb-156.md)
- Since v1.5.6, `duckdb.h` itself is versioned: `DUCKDB_API_VERSION_MAJOR/MINOR/PATCH` (default 1.5.6), `DUCKDB_API_VERSION_AT_LEAST(x,y,z)`, `DUCKDB_API_ALLOW_DEPRECATED`, `DUCKDB_API_ALLOW_UNSTABLE` (defaults from the legacy `DUCKDB_EXTENSION_API_VERSION_UNSTABLE`). `duckdb_extension.h` forwards `DUCKDB_EXTENSION_API_VERSION_*` into these and errors if both are set inconsistently. — [duckdb.h @ v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb.h), [duckdb_extension.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension.h)
- V1 unstable version string semantics (header comment): "An unstable extension is tied to one exact DuckDB build, so it reports that build's identity -- a tag or a commit hash -- rather than a semantic API version." — [duckdb_extension.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension.h)
- The C extension template (`duckdb/extension-template-c`, `main`) still defaults to `TARGET_DUCKDB_VERSION=v1.2.0` and `USE_UNSTABLE_C_API=0`, with the Makefile comment "Set to 1 to enable Unstable API (binaries will only work on TARGET_DUCKDB_VERSION, forwards compatibility will be broken)". Its README says "The DuckDB Extension C API has a stable part and an unstable part." No mention of v2 was found in the README lines matched. — [extension-template-c Makefile](https://raw.githubusercontent.com/duckdb/extension-template-c/main/Makefile), [README](https://raw.githubusercontent.com/duckdb/extension-template-c/main/README.md)
- Both `duckdb_extension.h` and `duckdb_extension_v2.h` still carry the generated banner "WARNING: this API is not yet stable, meaning it is only guaranteed to work for this specific DuckDB version." even at v1.5.6/v2.0.0 (the same banner is present in the v1 header at every tag checked). — [duckdb_extension.h @ v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h)

**V2 (`duckdb_extension_v2.h`, `duckdb_ext_api_v2`)**
- "The C API v2 is declared in the `duckdb_v2.h` header. Extensions that target it include `duckdb_extension_v2.h` instead of `duckdb_extension.h`; an extension targets either the v1 or the v2 C API, never both. Every v2 function is behind the `DUCKDB_V2_API_ALLOW_UNSTABLE` switch: define it to 1 before including the header, or define the older `DUCKDB_EXTENSION_API_VERSION_UNSTABLE`, from which it defaults. An extension built with `duckdb_extension_v2.h` opts in through the `build_loadable_extension_capi_unstable` and `build_static_extension_capi_unstable` build macros instead." — [docs/2.0/clients/c/v2/overview (source)](https://raw.githubusercontent.com/duckdb/duckdb-web/main/docs/2.0/clients/c/v2/overview.md)
- The V2 extension header refuses to compile without the unstable switch: "No V2 function has been stabilized yet, so without the unstable surface the function pointer struct would be empty." / `#error "the V2 C API has no stable surface yet: build with build_loadable_extension_capi_unstable or build_static_extension_capi_unstable, which tie the extension to this DuckDB version"`. — [duckdb_extension_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension_v2.h)
- V2 version macros: `DUCKDB_V2_API_VERSION_MAJOR/MINOR/PATCH` (default 2.0.0), `DUCKDB_V2_API_VERSION_AT_LEAST`, `DUCKDB_V2_API_VERSION_BELOW`, `DUCKDB_V2_API_ALLOW_DEPRECATED`, `DUCKDB_V2_API_ALLOW_UNSTABLE`; extension side `DUCKDB_EXTENSION_API_VERSION_MAJOR` must be 2. Header comment: "The unstable surface is not a promise, so it is not part of any released version: its constructs may change shape or vanish." — [duckdb_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_v2.h)
- Header comment on the version string: "The major selects the V2 API family; for extensions pinned to an exact DuckDB version (C_STRUCT_UNSTABLE) the loader reads only the major and ignores the rest." — [duckdb_extension_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension_v2.h)
- V2 entrypoint shape: `DUCKDB_EXTENSION_ENTRYPOINT(duckdb_v2_extension_handle extension, duckdb_v2_context_handle context, duckdb_v2_error_info_handle *err)`; the exported symbol is `<DUCKDB_EXTENSION_NAME>_init_c_api_v2(struct duckdb_v2_extension_input *input)`; `DUCKDB_EXTENSION_API_INIT` calls `input->get_api(input->extension, minimum_api_version)` and copies the result into a global `duckdb_ext_api_v2 duckdb_ext_api`. For static builds (`DUCKDB_BUILD_STATIC_EXTENSION`) no vtable is used. (V1 entrypoint instead receives `info` and `access` and returns bool.) — [duckdb_extension_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension_v2.h), [extension_load.cpp @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/main/extension/extension_load.cpp)
- V2 calling convention: functions return `DUCKDB_V2_ERROR` and take a trailing `duckdb_v2_error_info_handle *err`; results come back through output parameters; docs tag parameters as input / `(out)` / `(out, borrowed)` / `(ownership passes to the callee)`. — [docs/2.0/clients/c/v2/overview (source)](https://raw.githubusercontent.com/duckdb/duckdb-web/main/docs/2.0/clients/c/v2/overview.md), [duckdb_extension_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension_v2.h)
- The V2 surface is already changing after 2.0.0: `duckdb_v2.h` at `main` differs from `v2.0.0` in 1,663 diff lines. `v2.0.0` uses a `duckdb_v2_str {const char *ptr; idx_t len;}` view struct and `duckdb_v2_identifier_t`; `main` has removed these in favour of separate `const char *` + `idx_t length` parameters (e.g. `duckdb_v2_config_get_option_value`, `duckdb_v2_error_info_get_text`, `duckdb_v2_text_sink_fn`). 620 exported functions at `v2.0.0` vs 654 at `main`. — [duckdb_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_v2.h) vs [duckdb_v2.h @ main](https://raw.githubusercontent.com/duckdb/duckdb/main/src/include/duckdb_v2.h)
- This matches Maxxen's statement in Discussion #27525 (2026-10-20, paraphrased) that `duckdb_v2_str` would be removed before stabilisation because struct-by-value/pointer-to-struct strings cause problems for FFI and GC runtimes (Go, C#, Java named). — [Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)

### Inferences
- Practical compatibility matrix as of Nov 2026: (a) V1 pinned to 1.2.0 -> loads in 1.2.0+ including 2.0.0; (b) V1 pinned to 1.5.6 -> loads in 1.5.6+ including 2.0.0, and gets file system / copy / catalog / config-option / log-storage functions with a stable ABI; (c) V2 -> must be rebuilt for every DuckDB build (2.0.0 only today) and source-level breakage on the next release is already certain (the `duckdb_v2_str` removal on `main`); (d) C++ -> rebuilt per DuckDB version as always.
- An old V1 binary built with `USE_UNSTABLE_C_API=1` against <= 1.5.5 carries `C_STRUCT_UNSTABLE` and would be routed to the V2 entrypoint lookup in 2.0.0 and fail; such extensions must be rebuilt pinned to 1.5.6.
- If the reported plan holds (V1 deprecated at 2.0, removed at 3.0), V1 remains loadable for the whole 2.x line.

### Gaps
- `VERSIONING.md` (added by PR #24362) and `extension_load_v2.hpp` were not read; the exact rule the loader uses to accept/reject a `C_STRUCT_UNSTABLE` V2 binary built against a different DuckDB build was not verified in source.
- The "deprecate V1 at 2.0.0, remove at 3.0.0" plan comes from a tool summary of PR #24362, not a verbatim quote; no deprecation notice for V1 was seen in the 2.0 docs or headers checked.
- Observation needing confirmation: the V1 header at `v2.0.0` contains two function pointers inside the `AT_LEAST(1, 5, 6)` band that are absent from the header at tag `v1.5.6` (`duckdb_create_timestamp_tz_ns`, `duckdb_get_timestamp_tz_ns`). An extension built with 2.0.0 headers that calls them while declaring API v1.5.6 might not be safe on a real 1.5.6 binary. Not verified against DuckDB source or any maintainer statement. — [v1.5.6 header](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h) vs [v2.0.0 header](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension.h)
- Whether community-extensions CI already builds/distributes V2-C-API extensions for 2.0.0 was not checked.

## 3. What V2 adds over V1: function groups, with the version each landed

### Takeaway
Many headline capabilities (file system access, copy functions, config options, catalog lookup, log storage, scalar bind/init) already landed in V1 as unstable in v1.5.0 and became stable in v1.5.6; V2 (first shipped 2.0.0, all unstable) re-does the whole surface under `duckdb_v2_*` names and adds a much richer table function interface, COPY FROM/TO, multi-file readers, pragma and macro functions, custom options, log sinks, replacement scans as objects, expressions/filter pushdown, Arrow import/export and query metrics.

### Cited Findings
**V1 history (functions listed by the first release tag whose `duckdb_ext_api_v1` contains them; all of these were unstable until they were stabilised together in the v1.5.6 band)** — headers at [v1.2.0](https://raw.githubusercontent.com/duckdb/duckdb/v1.2.0/src/include/duckdb_extension.h), [v1.3.0](https://raw.githubusercontent.com/duckdb/duckdb/v1.3.0/src/include/duckdb_extension.h), [v1.4.0](https://raw.githubusercontent.com/duckdb/duckdb/v1.4.0/src/include/duckdb_extension.h), [v1.5.0](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.0/src/include/duckdb_extension.h), [v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h)
- v1.2.0 (stable base, 404 slots: connections, queries, results, values, logical types, data chunks, vectors, scalar/aggregate/table/cast function registration, replacement scans, appender, table descriptions, profiling, etc.) plus unstable: `duckdb_create_instance_cache`, `duckdb_get_or_create_from_cache`, `duckdb_destroy_instance_cache`, `duckdb_append_default_to_chunk`.
- v1.3.0 (unstable, 20): client context (`duckdb_connection_get_client_context`, `duckdb_client_context_get_connection_id`, `duckdb_destroy_client_context`), scalar function bind (`duckdb_scalar_function_set_bind`, `duckdb_scalar_function_bind_set_error`, `duckdb_scalar_function_set_bind_data`, `duckdb_scalar_function_get_bind_data`, `duckdb_scalar_function_get_client_context`), vectors (`duckdb_create_vector`, `duckdb_destroy_vector`, `duckdb_slice_vector`, `duckdb_vector_reference_value`, `duckdb_vector_reference_vector`, `duckdb_create_selection_vector`, `duckdb_destroy_selection_vector`, `duckdb_selection_vector_get_data_ptr`), values (`duckdb_create_map_value`, `duckdb_create_union_value`, `duckdb_value_to_string`), `duckdb_get_table_names`.

## 4. Relevant PRs / discussions and maintainers' statements about direction

### Takeaway
Maintainers present V2 as the intended single API for both clients and extensions, with V1 frozen (no new functions) and slated for deprecation; C++-internal-API features such as catalog/storage, optimizer and parser extensions are "planned eventually" or not near, so C++ is not being replaced for those extension classes yet.

### Cited Findings
- Discussion #27525 "Everything C API v2!" (evertlammerts, 2026-10-20): V2 is "a ground-up rewrite meant to be the single API for building extensions and clients" (paraphrase); asks for feedback incl. on the `duckdb::cxx` wrapper and new Rust bindings. — [Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)
- PR #24362 (Maxxen, merged 2026-08-03 into `v1.5-variegata`): unified versioning, stabilised all V1 APIs in v1.5.6, "Don't add new functions to the V1 C API" guidance for contributors, V1 deprecation planned at 2.0.0 and removal at 3.0.0 (paraphrase). Follow-up to `main`: PR #24435. — [PR #24362](https://github.com/duckdb/duckdb/pull/24362)
- PR #25916 "C-API-V2: Add custom file system support" (Maxxen): **open** as of 2026-11-13, targets `main` (rebased from `v2.0-cyanoptera` on 2026-10-14), description "PR description pending."; commit titles mention a "vfs" and "per operation handles". A user asked on 2026-11-13 whether it is planned for an upcoming release; no reply. — [PR #25916](https://github.com/duckdb/duckdb/pull/25916)
- Maxxen in #27525 (2026-10-20/21, paraphrased): targeting the C API gives faster builds and smaller binaries even before stabilisation; dedicated extension-development tooling (signing, footer updating) is planned; `duckdb::cxx` will get a CMake `find_package` module; an ABI-check function for clients is being considered (`duckdb_v2_library_version` exists but does not indicate ABI). — [Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)
- Community signal in #27525: rustyconover (Query.Farm) states he maintains about 45 community extensions rebuilt per release for v1.4, v1.5 and v2.0, and lists blocking gaps for porting to V2 (see section 5). — [Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)

## 5. Known limitations / gaps of the C API (V2 and V1) vs the C++ extension API

### Takeaway
As of 2.0.0, V2 cannot register custom file systems, has no secrets/HTTP, catalog/storage, optimizer/parser/operator extension points, table in-out or window functions, appender, or SQL execution from callbacks; its expression/filter-pushdown API is expected to change; and nothing in it is ABI-stable. These all remain C++-only (or V1-only, for the appender).

### Cited Findings
- Verified by name search of the 2.0.0 and `main` headers: zero `duckdb_v2_*` functions contain `secret`, `appender`, `http`, `catalog`, `optimizer`, `storage`, `window`, or `in_out`; `virtual_column` appears only on `main` (`duckdb_v2_table_function_add_virtual_column`). — [duckdb_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_v2.h), [duckdb_v2.h @ main](https://raw.githubusercontent.com/duckdb/duckdb/main/src/include/duckdb_v2.h)
- Maintainer statements in Discussion #27525 (Maxxen, 2026-10-20/21; paraphrased from a summary of the page): — [Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)
  - Not yet available, need core changes first: statistics, optimizer extensions, custom operators, custom client/instance state, secrets.
  - Secrets and HTTP: planned, on hold because both are undergoing significant changes in core.
  - Storage/catalog extensions: planned eventually, very large surface; catalog extensions for SQLite/MySQL/Postgres are blocked on it; a catalog access interface is planned.
  - Custom file system *registration*: in progress in PR #25916 (not in 2.0.0).
  - Table in-out functions: not supported; likely later as separate bind/exec callbacks with sink/source semantics.
  - Running SQL from inside callbacks: intentionally left out (connection is busy; a second connection loses transactionality); a PRAGMA function is suggested as a workaround, and a `context_get_instance`/`extension_get_instance` accessor is being considered.
  - Expression / filter pushdown API: "known to be defective" and likely to change significantly before stabilisation.
  - Custom types: blocked on core binding/storage work.
  - Parser extensions: possibly later once the PEG parser matures; optimizer/planner stabilisation "not near".
  - Lifecycle callbacks and per-database state (ObjectCache-like): to be added.
  - No V2 appender; users can build one with `column_data_collection`.
  - Transactions: explicit begin/commit/rollback API suggested but not present.
  - No runtime ABI version check yet.
- User-reported blocking gaps (rustyconover, 2026-10-20): running queries, instance access, secrets, HTTP, storage/catalog, in-out and window functions, cancellation, custom types, Arrow extension types. — [Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)
- Stability gap: "No V2 function has been stabilized yet" — a V2 binary is tied to the exact DuckDB version, same as a C++ extension today. — [duckdb_extension_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension_v2.h)
- V1 limitations relative to V2 (from header comparison): V1 has no filter pushdown, partitioning, progress, cardinality-with-order hints, glob/exists/remove file-system helpers, pragma/macro registration, multi-file hook, or COPY TO batching callbacks; V1 does have an appender and catalog-entry lookup, which V2 lacks by name. — [duckdb_extension.h @ v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h), [duckdb_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_v2.h)
- V1 is frozen: contributors are told not to add new functions to the V1 C API (paraphrase). — [PR #24362](https://github.com/duckdb/duckdb/pull/24362)

### Inferences
- Statistics and virtual columns moved from "not available" (Oct 20 statement) to present on `main` within about four weeks, indicating fast iteration on the unstable surface; expect further breaking changes before 2.1.
- For a table-function + file-reading extension, none of the listed gaps is blocking except (a) no ABI stability and (b) inability to register a custom/virtual file system; consuming DuckDB's file systems (including remote ones provided by other extensions) is available.

### Gaps
- An authoritative, maintained "C API vs C++ API feature matrix" was not found.
- The V1 list of what cannot be done vs C++ was derived from header comparison, not from a DuckDB document; V1's `duckdb_table_function_supports_projection_pushdown` and other stable-base functions were not enumerated individually.
- Thread-safety and performance characteristics of V2 callbacks vs the C++ API were not researched.
