# Rewrite pcapsql-duckdb on stable V1, stage V2

DuckDB's "C API v2" is a ground-up, separately named API family (`duckdb_v2.h`, 620 `duckdb_v2_*` functions) that shipped in DuckDB 2.0.0 on 2026-10-21, and as of 15 November 2026 **not one of its functions is stable**: a V2 extension loads only in the exact DuckDB build it was compiled against, and the header on `main` has already broken source compatibility with the 2.0.0 tag. It is nonetheless the first C interface that gives a file-reading extension nearly the whole C++ table-function surface: filter pushdown, per-thread state, progress, a multi-file wrapper (globs, `filename`, hive partitioning), glob and positional reads on DuckDB's file system, replacement scans and extension-owned macros. For pcapsql the recommendation is to **rewrite now on the frozen V1 API pinned at v1.5.6 (the `duckdb` 1.20000.x crate plus raw file-system FFI), keep the DuckDB-facing code thin, and port that thin layer to V2 through `duckdb-neo` once DuckDB 2.1 stabilises table functions and the file system**. Staying as is is not a real option: the committed build stamps `C_STRUCT_UNSTABLE` for DuckDB v1.4.2 while the lockfile binds DuckDB 2.0.0 headers, and DuckDB 2.0 routes that ABI tag to a V2 entrypoint the extension does not export. Most of what the rewrite would gain for pcapsql (reads through DuckDB's file system including `s3://`, projection pushdown into `ParseScope`, parallel scans, real errors, load tests, a binary that works across 1.5.6 and 2.x) needs only V1 at 1.5.6; the V2-only gains (filter pushdown, engine-provided globbing, `FROM 'x.pcap'`) are real but secondary and sit on the least settled part of the API. One discrepancy in the research notes is resolved here: `duckdb-neo` **is** on crates.io (0.20000.2, 2026-11-13), contrary to a maintainer remark from 20 October.

## V2 shipped in DuckDB 2.0.0 with zero stable functions

The quoted sentence comes from the DuckDB 2.0 C documentation, which opens with a warning: "The C API v2 is not yet stable. Its interface may change in upcoming releases", followed by "DuckDB 2.0 ships a revamped C API, which is considerably more powerful than its predecessor. Among others, it exposes components such as file systems and table functions to extensions" ([C API v2 overview, source](https://raw.githubusercontent.com/duckdb/duckdb-web/main/docs/2.0/clients/c/v2/overview.md)). The 2.0.0 release announcement repeats it and adds "Before marking it as stable, we would like to test it in the field" ([Announcing DuckDB 2.0.0, source](https://raw.githubusercontent.com/duckdb/duckdb-web/main/_posts/2026-10-21-announcing-duckdb-200.md)). DuckDB 2.0.0 is the latest release and an LTS with end of life 2027-10-22; no 2.0.1 or 2.1.0 tag existed on 15 November ([past_releases.csv](https://raw.githubusercontent.com/duckdb/duckdb-web/main/_data/past_releases.csv)).

V2 is a second API family, not a new version of `duckdb.h`. Extensions include `duckdb_extension_v2.h`, export `<name>_init_c_api_v2`, and target "either the V1 or the V2 C API, never both"; the header refuses to compile without the unstable switch because "No V2 function has been stabilized yet, so without the unstable surface the function pointer struct would be empty" ([duckdb_extension_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension_v2.h)). All 654 lifecycle entries in the V2 spec on `main` read `unstable v2.0.0` ([api_spec/v2](https://github.com/duckdb/duckdb/tree/main/api_spec/v2)). The consequence is the pinned build mode: ABI type `C_STRUCT_UNSTABLE`, where "DuckDB will only load your extension into if it has the exact same version you built against" ([VERSIONING.md](https://github.com/duckdb/duckdb/blob/main/api_spec/VERSIONING.md)). That is the same distribution burden as a C++ extension.

Breakage on the next release is already certain rather than hypothetical. `duckdb_v2.h` on `main` differs from the 2.0.0 tag in 1,663 diff lines: the `duckdb_v2_str` and `duckdb_v2_identifier_t` string structs used throughout 2.0.0 have been replaced by `const char *` plus length parameters, and 34 functions were added (statistics, virtual columns, profiler metrics) ([duckdb_v2.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_v2.h), [duckdb_v2.h @ main](https://raw.githubusercontent.com/duckdb/duckdb/main/src/include/duckdb_v2.h)). The roadmap, last updated November 2026, lists "Stabilizing the C API v2 and the C extension API" among items in flight for DuckDB 2.1, with an explicit no-guarantees caveat ([roadmap.md](https://raw.githubusercontent.com/duckdb/duckdb-web/main/roadmap.md)). In the feedback thread a maintainer said function registration would be stable "surely for 2.1" and that the expression and filter-pushdown API is known to be defective and likely to change significantly; these are paraphrases from a summarised page, not verbatim quotes ([Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)). No release date for 2.1 was found.

The stable alternative was created deliberately in the run-up to V2. DuckDB 1.5.6 (2026-09-28) stabilised every remaining unstable V1 function and froze V1: the V1 vtable now has exactly two bands, 404 slots at v1.2.0 and 142 at v1.5.6, and an extension that pins API 1.5.6 with ABI type `C_STRUCT` is loadable by "Any DuckDB at or above it" ([VERSIONING.md](https://github.com/duckdb/duckdb/blob/main/api_spec/VERSIONING.md)). The 2.0.0 loader states the rule directly: "C_STRUCT_UNSTABLE always means V2: everything that was unstable in the V1 API was stabilized into v1.5.6, so a V1 extension pins that version rather than building against 'unstable'" ([extension_load.cpp @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/main/extension/extension_load.cpp)). V1 receives no new functions; the PR that froze it reportedly plans deprecation at 2.0 and removal at 3.0, which would keep V1 loadable for the whole 2.x line, but that plan is a paraphrase and no deprecation notice appears in the 2.0 docs or headers ([PR #24362](https://github.com/duckdb/duckdb/pull/24362)).

## V2 hands a file reader pushdown, globbing and per-thread state

Many headline capabilities attributed to V2 already exist in stable V1. File-system access, copy functions, config options, catalog lookup and client-context access landed in V1 as unstable in 1.5.0 and became stable in 1.5.6 ([duckdb_extension.h @ v1.5.6](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/include/duckdb_extension.h)). What V2 adds is depth. The table below compares what matters to a pcap reader; V1 rows come from the generated spec ([v1 table_function.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v1/table_function/table_function.yaml), [v1 file_system.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v1/file_system/file_system.yaml)), V2 rows from ([v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml), [v2 file_system.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/filesystem/file_system.yaml)), and the pcapsql column from the local audit.

| Capability | V1 pinned at 1.5.6 (stable) | V2 at 2.0.0 (unstable) | pcapsql-duckdb today |
|---|---|---|---|
| Binary compatibility | 1.5.6 and later, including 2.0.0 | exact DuckDB build only | broken stamp (see below) |
| Read via DuckDB file system | open, read, write, seek, tell, size, sync, close | adds glob, exists, is-remote, `read_at`, parallel-access and file-cache flags | no, `std::fs` only |
| Projection pushdown | yes | yes | no |
| Filter pushdown | no | yes, accept-style over bound expressions | no |
| Parallel scan | `max_threads` plus local init | `max_threads`, typed local state, batch claiming | no, one mutex-guarded reader |
| Cardinality hint | yes | yes, plus order preservation | no |
| Progress reporting | no | yes | no |
| Named parameters | yes | yes, with defaults and variadics | no |
| Multi-file (glob, lists, `filename`, hive) | no, hand-built | engine wrapper around a single-file function | no |
| Client context in callbacks | bind only | every callback | n/a |
| Replacement scan | needs a `duckdb_database` handle | registrable object | no |
| SQL macros | run `CREATE MACRO` on load connection | `extension_register_macro_function` | `CREATE MACRO` at load |
| Statistics, virtual columns | no | `main` only, not in 2.0.0 | no |

Three points in that table deserve interpretation. First, V2 filter pushdown is strict: accepting a predicate "is a promise to filter the rows exactly as it would have", and the optimizer may invoke the callback more than once; a looser hint path exists only for functions that also enable projection pushdown, typically when wrapped by a multi-file function ([v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)). Second, the multi-file wrapper is the most valuable V2-only feature for capture directories, but no in-tree test references `multi_file_function`, so its maturity is unverified ([v2 table.yaml](https://github.com/duckdb/duckdb/blob/main/api_spec/v2/function/table.yaml)). Third, both families only consume DuckDB's file system. Registering a custom one is an open PR against `main` ([PR #25916](https://github.com/duckdb/duckdb/pull/25916)), and neither API exposes a compression option, so compressed files arrive as raw bytes ([capi_v2_file_system.cpp](https://github.com/duckdb/duckdb/blob/main/src/main/capi/v2/capi_v2_file_system.cpp)).

V2 also has gaps that do not touch a reader: no secrets, HTTP, catalog or storage extensions, optimizer or parser hooks, table in-out functions, appender, or SQL execution from callbacks ([Discussion #27525](https://github.com/duckdb/duckdb/discussions/27525)). None blocks pcapsql. One conclusion follows from the two columns together: a stable binary across DuckDB versions combined with filter pushdown or multi-file reading is not achievable by any route today.

## Rust support is ahead of the C API's stability

The upstream `duckdb-rs` repository now ships two wrappers on one sys crate. The classic `duckdb` crate (1.20000.2, 2026-11-13) wraps V1; its `VTab` trait offers bind, init, func, projection pushdown, named parameters, cardinality and `set_max_threads`, but **no local-init method, no filter pushdown and no file-system wrapper** ([vtab/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb/src/vtab/mod.rs)). The V1 file-system functions are present as raw `ffi::` functions in the loadable bindings ([bindgen_bundled_version_loadable.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/libduckdb-sys/src/bindgen_bundled_version_loadable.rs)). The new `duckdb-neo` crate wraps V2 with typed bind, local and global state, `TableFilterPushdownCallbacks`, progress, partitioning, a `MultiFileFunctionBuilder` and a safe `FileSystem`/`File` API with `glob` and `read_at` ([table_function/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/src/table_function/mod.rs), [file.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/src/file.rs)). Its loadable build is "pinned to the exact DuckDB build `duckdb-neo` was built against" ([extensions.md](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb-neo/extensions.md)).

**Discrepancy flagged.** The overview notes relay a maintainer comment, dated 2026-10-20 and paraphrased from a summarised page, that `duckdb-neo` was not yet on crates.io. The Rust ecosystem notes queried the crates.io API directly: `duckdb-neo` was first published as 0.20000.0 on 2026-10-22, with 0.20000.2 on 2026-11-13 and about 2.4k downloads ([crates.io duckdb-neo](https://crates.io/crates/duckdb-neo)). The crates.io record is the more direct evidence and the two statements are consistent in time: the crate was published two days after the comment. The README now calls it beta ("Not experimental anymore, now in beta", commit of 2026-11-09) ([duckdb-rs README](https://github.com/duckdb/duckdb-rs/blob/main/README.md)).

Three smaller disagreements resolve the same way. The table-function notes found no public C-API extension that reads through `duckdb_file_system_open`, but the ecosystem notes, which cloned community extensions, found two: duckdb-zarr and laterite. The ecosystem and table-function notes found no primary statement on when V2 stabilises, while the overview notes read the roadmap source and found the 2.1 item. And the PR text reportedly says "about 189 functions were stabilized" in 1.5.6, whereas the header contains 142 slots in that band; the difference is unexplained.

Upstream direction is clear. The official Rust extension template moved to `duckdb-neo` and V2 on 2026-10-23, with `CAPI_VERSION=2`, `USE_UNSTABLE_C_API=1` and the note that binaries "load only in the exact TARGET_DUCKDB_VERSION, not in newer DuckDB releases" ([extension-template-rs Makefile](https://github.com/duckdb/extension-template-rs/blob/main/Makefile)). The community repository already builds neo-based extensions, and supports per-release refs (`ref`, `andium`, `variegata`) so one project can serve several DuckDB lines from different commits ([community-extensions build.py](https://github.com/duckdb/community-extensions/blob/main/scripts/build.py)).

The best prior art for the stable route is duckdb-zarr: `duckdb = "=1.20000.0"`, V1 entrypoint, C API floor v1.5.6, DuckDB file system through raw FFI, projection pushdown and `set_max_threads`. Its Makefile states the reasoning: "DuckDB 1.5.6 froze the v1 C API, including the filesystem functions this adapter uses. Keep the v1 entrypoint on DuckDB 2.0 instead of advertising C_STRUCT_UNSTABLE, which would select the incompatible v2 entrypoint" ([duckdb-zarr Makefile](https://github.com/xqlsystems/duckdb-zarr/blob/main/Makefile), [duckdb_store.rs](https://github.com/xqlsystems/duckdb-zarr/blob/main/src/zarr_reader/duckdb_store.rs)). The only existing pcap extension, `pcap_reader`, is a single-threaded V1 `VTab` built against DuckDB 1.3.0 with a fixed eight-column schema that reads with `std::fs::File` and `ehttp` rather than DuckDB's file system ([quackscience/duckdb-extension-pcap](https://github.com/quackscience/duckdb-extension-pcap)). pcapsql's niche of full protocol tables inside DuckDB is unoccupied.

## The current extension is not a baseline worth keeping

The audit of the local crate shows a developer-machine artifact, not a shippable extension. The manifest declares `duckdb = "1.4"` while the lockfile resolves `duckdb` and `libduckdb-sys` to 1.20000.0, which under duckdb-rs's version scheme is DuckDB 2.0.0 ([pcapsql-duckdb/Cargo.toml](../pcapsql-duckdb/Cargo.toml), [Cargo.lock](../Cargo.lock)). The Makefile hard-codes one developer's DuckDB CLI path, `DUCKDB_VERSION = v1.4.2`, `linux_amd64`, and stamps `--abi-type C_STRUCT_UNSTABLE` ([pcapsql-duckdb/Makefile](../pcapsql-duckdb/Makefile)). By the loader rule quoted above, DuckDB 2.0.0 will look for `pcapsql_init_c_api_v2` in such a binary and reject it; whether it loads safely in DuckDB 1.4.2 with 2.0.0-generation bindings is unverified. No CI job builds, loads or packages the extension, and no test loads it into DuckDB ([ci.yml](../.github/workflows/ci.yml)).

Functionally, all 30 table functions are single-file, single-threaded behind a mutex, parse every packet with `ParseScope::full()`, and implement no projection pushdown, filter pushdown, cardinality, named parameters or globbing ([read_pcap.rs](../pcapsql-duckdb/src/vtab/read_pcap.rs), [protocol_tables.rs](../pcapsql-duckdb/src/vtab/protocol_tables.rs)). Paths go straight to `std::fs`, so `s3://` and `https://` never work, and per the quack-rs measurements such reads bypass DuckDB's `enable_external_access` and `allowed_directories` settings ([quack-rs known-limitations](https://github.com/tomtom215/quack-rs/blob/main/book/src/reference/known-limitations.md)). Read errors other than the string-matched "batch full" sentinel are treated as end of file, so a truncated capture yields a silently short result. Protocol tables carry no timestamp column, and the `frames` timestamp is a BIGINT of microseconds with nanosecond precision dropped ([duckdb_schema.rs](../pcapsql-duckdb/src/duckdb_schema.rs)).

The audit also reasoned, without executing anything, to several likely defects: `dns.answer_ip6s` is always a NULL list when it has elements, `read_pcap` can write past 2048 rows in one chunk for tunnelled traffic, and the crate docs show `format_ip4(src_ip)` against a column that is actually VARCHAR ([batch_builder.rs](../pcapsql-duckdb/src/vtab/batch_builder.rs), [lib.rs](../pcapsql-duckdb/src/lib.rs)). These are inferences from source and need a load-and-query test to confirm. They are the class of bug that only such a test catches, and none exists.

## V1 at 1.5.6 delivers most of the gain; V2 is the destination

The decision turns on which gains require V2. Sorted by where they become available, the picture is lopsided.

**Gains available on V1 pinned at 1.5.6.** pcapsql-core's reader stack is generic over synchronous `std::io::Read`, and a ready-made any-`Read` source exists in `StdinPacketSource::from_reader` ([pcap_stream.rs](../pcapsql-core/src/io/pcap_stream.rs), [stdin.rs](../pcapsql-core/src/io/stdin.rs)). A small adapter implementing `Read` over a DuckDB file handle therefore gives sequential scans of local and remote paths through whatever file systems the user has loaded, with DuckDB's access controls applied. Remote secret resolution on V1 is inferred from the implementation calling `FileSystem::GetFileSystem(context)`, not confirmed by a test ([file_system-c.cpp](https://github.com/duckdb/duckdb/blob/main/src/main/capi/v1/file_system-c.cpp)). Core's own `DecompressReader` detects gzip and zstd by magic bytes, so the C file system's lack of decompression costs pcapsql nothing ([decompress.rs](../pcapsql-core/src/io/decompress.rs)). Projection pushdown maps onto core's existing `ParseScope`, a follow-up the design doc already tracks ([query-scoped-parse-migration.md](../docs/query-scoped-parse-migration.md)). Parallel scans map onto `SeekablePacketSource::partitions` and `reader_at`, for uncompressed files, with `set_max_threads` ([source.rs](../pcapsql-core/src/io/source.rs)). Named parameters, a cardinality hint, real error propagation from `func`, TIMESTAMP columns on protocol rows, a column-typed chunk writer, and load tests against DuckDB 1.5.6 and 2.0.0 in CI all need nothing newer. The result is one binary for DuckDB 1.5.6 and every later release that keeps V1.

**Gains that require V2.** Filter pushdown lets a scan skip work for predicates on `frame_number` or timestamp by consulting core's boundary index; predicates on parsed protocol fields still require parsing, so the benefit is narrower for pcap than for a columnar format with statistics. The multi-file wrapper supplies globs (including remote ones), file lists, a `filename` column and hive partitioning, which matters for directories of rotated captures. Typed per-thread state removes the `Mutex` or hand-written `extern "C"` workaround that V1's `VTab` forces. Progress bars, `SELECT * FROM 'trace.pcap'` via a registrable replacement scan, extension-owned macros, and a context handle in every callback complete the list. These are user-visible improvements, not prerequisites.

**The recommendation.** Rewrite now on V1 pinned at 1.5.6, using `duckdb` 1.20000.x `VTab` and `VScalar` plus a small unsafe module of raw `ffi::duckdb_file_*` calls modelled on duckdb-zarr. Stamp the binary `C_STRUCT` with API version v1.5.6 and set `min_duckdb_version = "v1.5.6"` explicitly on the entrypoint macro. Put the engine-independent logic (a DuckDB-backed `PacketSource`, scan planning from projected columns to `ParseScope`, partition assignment, the chunk writer's column plan) behind an internal interface, so the DuckDB-facing glue is the only part a V2 port replaces. Prototype the `duckdb-neo` port on a branch against the official template's `sequence.rs` example, and switch the shipping path when DuckDB 2.1 marks the table-function and file-system modules stable, or earlier if remote globbing becomes a hard requirement.

Three facts specific to pcapsql drive this over going straight to V2. The crate's git history is eight commits, all side effects of core changes, so it gets little dedicated attention; a pinned V2 build demands a rebuild and probably source changes at every DuckDB release, while a V1 binary at 1.5.6 keeps loading. The V2 pieces pcapsql would most want, filter pushdown and the multi-file wrapper, are respectively the part maintainers call defective and the part with no in-tree test. And the extension has no distribution channel yet, so its first job is to become loadable, tested and correct, which is API-independent work.

The case for V2 now deserves a fair statement. Nothing ships today, so there are no users to break. The community pipeline rebuilds per DuckDB release anyway, which reduces the version pin to a rebuild rather than a distribution problem. `duckdb-neo`'s safe `FileSystem` avoids writing unsafe FFI that will be discarded, V1's client context is available only at bind, and the official template has already moved. If the maintainers intend to publish through community extensions, target only the latest DuckDB, and can absorb beta churn every few weeks, V2 through `duckdb-neo` with an exact `=0.20000.x` pin is defensible. The staged plan captures most of that upside later at lower risk, at the cost of writing the glue layer twice.

Risks on the recommended path are known and manageable. The V1 header in DuckDB 2.0.0 contains two slots (`duckdb_create_timestamp_tz_ns`, `duckdb_get_timestamp_tz_ns`) inside the 1.5.6 band that the real 1.5.6 header lacks, and `duckdb_rs_extension_api_init` copies every field of its compile-time struct layout; the notes infer, without confirmation from DuckDB, that bindings newer than the host could read past the host's struct ([duckdb_extension.h @ v2.0.0](https://raw.githubusercontent.com/duckdb/duckdb/v2.0.0/src/include/duckdb_extension.h), [quack-rs known-limitations](https://github.com/tomtom215/quack-rs/blob/main/book/src/reference/known-limitations.md)). Never call those two functions and load-test on both 1.5.6 and 2.0.0. The legality of using a client context or file-system handle obtained in bind from later phases and other threads is undocumented in V1; duckdb-zarr does it with `unsafe impl Send`/`Sync`. `extension-ci-tools` uses one variable for both the API stamp and the test engine, which duckdb-zarr works around in its Makefile. Panics are contained only for callbacks registered through the wrapper and only with `panic = "unwind"` ([vtab/mod.rs](https://github.com/duckdb/duckdb-rs/blob/main/crates/duckdb/src/vtab/mod.rs)). DuckDB 1.4 LTS users are excluded, but per a secondary source that line's support ends in late November 2026 ([quack-rs README](https://github.com/tomtom215/quack-rs/blob/main/README.md)).

## Conclusion

The framing of "V2 versus V1" overstates what the API choice decides. The file-system access that the V2 announcement advertises has been stable in V1 since 1.5.6, and pcapsql-core's synchronous, `Read`-generic design with built-in decompression and a seekable partition interface means the hard parts of a good DuckDB reader are already written. What V2 changes for pcapsql is the ceiling: predicate-driven skipping, engine-managed multi-file scans and first-class SQL ergonomics. That ceiling is worth reaching, but only once DuckDB promises not to move it.

The signals to watch are concrete: a DuckDB 2.1 release in which the table-function, file-system and multi-file entries of `api_spec/v2` change from `unstable` to `stable`, a `duckdb-neo` release that builds `C_STRUCT` rather than `C_STRUCT_UNSTABLE` extensions, and the merge of custom file-system registration. Open questions that this research could not settle are the 2.1 release date, whether the V1 removal-at-3.0 plan is official, and how V1 file handles behave across threads and against remote file systems in practice; the last one is cheap to answer with the load tests the rewrite needs anyway.
